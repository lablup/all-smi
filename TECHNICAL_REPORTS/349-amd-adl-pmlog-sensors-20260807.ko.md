# 기술 보고서: PR #349 - PMLog를 통한 Windows AMD ADL 센서 보강

**일자**: 2026-08-07  
**상태**: 코드 경로 기준 완료, 센서 인덱스 매핑과 하드웨어 기준은 미해결 (6절 참조)  
**관련 항목**: PR #349, 이슈 #347, PR #348 / 이슈 #346 위에 구축  
**위험 수준**: 중간 (기본 CI가 컴파일하지 않는 타겟의 손으로 전사한 벤더 ABI)

---

## 요약

PR #349는 `ADL2_New_QueryPMLogData_Get`에서 Windows AMD 온도, 보드 전력, 팬 속도, 클럭을 읽는 `src/device/readers/amd_adl.rs`를 추가했습니다. #348의 DXGI/PDH 계층은 WDDM이 게시하는 모든 것을 덮지만 이 네 가지는 덮을 수 없습니다. Windows가 아예 노출하지 않기 때문입니다.

`atiadlxx.dll`은 `libloading`을 통해 절대 경로 `C:\Windows\System32\atiadlxx.dll`에서 런타임에 로드되며, 맨 이름으로도 import 라이브러리로도 로드하지 않습니다. 따라서 실행 파일의 import 테이블에 `atiadlxx` 항목이 없고, AMD 드라이버가 없는 머신은 정상적으로 기동해 ADL 데이터만 보고하지 않습니다.

---

## 1. 문제 정의

#348 이후 Windows AMD 호스트는 사용률과 메모리는 얻었지만 온도, 보드 전력, 팬 속도, 클럭이 없었습니다. 이 넷은 Windows에서 WMI, DXGI, PDH 어느 쪽에도 소스가 없으므로 유일한 획득 경로가 AMD 자체 라이브러리입니다.

그 라이브러리는 CI가 컴파일하지 않는 타겟에 대해 손으로 전사한 FFI 표면이므로, 실패 모드를 먼저 밝혀 둘 가치가 있습니다. 잘못된 센서 인덱스는 크래시를 내지 않고 그럴듯하지만 틀린 값을 보고하며, 그럴듯하게 틀린 값은 값이 없는 것보다 나쁩니다.

## 3. 기술적 선택과 그 이유

### 3.1 우선순위는 WMI < DXGI/PDH < ADL

ADL은 OS의 회계값이 아니라 하드웨어 자신의 텔레메트리를 읽으므로, PDH 사용률을 덮어쓰고 온도, 전력, 팬, 클럭에 대해서는 유일한 소스가 됩니다.

### 3.2 레거시 Overdrive 경로는 의도적으로 미구현

센서는 `ADL2_Overdrive_Caps`로 게이트된 `ADL2_New_QueryPMLogData_Get`에서만 옵니다. OD5, OD6, OD7은 테스트할 방법이 없는 ABI 표면 세 개를 더 정확히 맞춰야 하는 일이며, 대상은 all-smi가 겨냥하는 카드보다 앞선 하드웨어입니다. Vega 이전 카드는 DXGI/PDH 기준선을 유지합니다.

### 3.3 `AdapterInfo`를 선언하지 않았으므로 보강은 AMD GPU가 정확히 하나일 때만

이 PR의 핵심 제약입니다. `AdapterInfo`는 PCI bus/device/function과 PNP 문자열을 담은 구조체로, ADL 어댑터 인덱스를 특정 카드에 묶을 수 있게 해 주는 것입니다. ADL은 **자기** `sizeof`를 기준으로 쓰기 때문에, 레이아웃 실수는 깔끔한 실패가 아니라 호출자 버퍼 오버플로가 됩니다. 게다가 카드 하나가 디스플레이 출력마다 하나씩 여러 어댑터 인덱스를 노출하며 전부 동일한 텔레메트리를 보고하는데, 그 구조체 없이는 중복 제거도 할 수 없습니다.

추측하는 대신 `can_attribute()`가 AMD GPU 단일 구성을 요구하도록 했습니다. 다중 AMD GPU 호스트는 한 카드의 온도가 다른 카드에 붙는 대신 정직한 DXGI/PDH 기준선을 받습니다. 이는 어댑터 매칭에 대해 #346 리뷰가 도달한 결론과 같습니다. 잘못 귀속하느니 귀속을 거절하는 편이 낫습니다. 이 제약은 이후 PR #361이 구조체를 선언하면서 해제했습니다.

### 3.4 센서 인덱스가 가장 약한 지점이며 그렇게 취급했다

`ADLSensorType` 인덱스는 AMD 공개 `adl_structures.h`에서 전사했습니다. CI가 all-smi를 Windows용으로 컴파일하지 않고 어떤 테스트도 실제 라이브러리를 호출할 수 없으므로, AMD가 항목 번호를 바꿨다면 엉뚱한 센서를 읽게 됩니다. 완화책은 두 가지입니다.

1. **범위 가드.** 모든 값을 물리적으로 타당한 대역에 대해 검사합니다(온도 0~150 C, 전력 0~1000 W, 활동률 0~100% 등). 인덱스가 어긋난 읽기는 거의 항상 목표 대역 밖에 떨어지므로, 가드가 조용히 틀린 값을 없는 값으로 바꿉니다. 클럭 값을 온도 슬롯에 넣고 판독 전체가 비어서 돌아오는지 단언하는 테스트가 있습니다.
2. **`amd.adl.sensors` 진단 검사가 원시 `index=value` 표를 덤프합니다.** 필터도 이름도 없이 그대로 냅니다. 이로써 코드 변경을 먼저 배포하지 않고도 실제 하드웨어에서 매핑을 확인할 수 있습니다. 모든 센서가 범위 가드에 걸리면, 검사는 이것이 바로 enum이 밀렸을 때의 모습이라고 명시하고 덤프를 요청합니다.

`amd.adl.library`는 별도로 네 상태를 구분합니다. DLL 없음, DLL은 있으나 컨텍스트 생성 실패, 로드됐으나 PMLog 가능 어댑터 없음, 선택된 어댑터 인덱스와 함께 정상.

### 3.5 DXGI 팩토리 캐싱, 이 PR에 함께 실림

폴링 오버헤드에 대한 질문에서 촉발됐습니다. `CreateDXGIFactory1`은 그래픽 드라이버 DLL을 끌어올 수 있는 COM 객체 생성인데, #348이 이를 매 폴링마다, 많게는 초당 한 번 실행했습니다. 이제 한 번 생성하고 `IDXGIFactory1::IsCurrent`가 어댑터 집합 변경을 보고할 때만 재생성하며, 이는 핫플러그 정확성도 함께 유지합니다.

비용에 대해 기록해 둡니다. **두 계층 중 어느 것도 GPU 작업을 제출하지 않습니다.** DXGI는 어댑터 디스크립터를 읽고, PDH는 OS가 이미 유지하는 카운터를 읽으며, ADL은 드라이버가 이미 수집하는 텔레메트리 블록을 읽습니다. 부하는 CPU 측이며 작습니다. 라이브러리 로드, ADL 컨텍스트 생성, PMLog 능력 스캔은 각각 프로세스당 한 번이므로 정상 상태 폴링은 ADL 호출 하나입니다.

모듈에 문서화한 주의사항이 하나 있습니다. 매우 공격적인 센서 폴링(데스크톱 모니터링 도구가 쓰는 100 ms 주기)은 AMD GPU를 가장 깊은 유휴 상태에 들어가지 못하게 잡아 둘 수 있습니다. all-smi의 간격은 1초에서 시작하므로 그 범위에서 충분히 떨어져 있습니다.

## 4. 검증 결과

#348과 동일한 제약입니다. all-smi를 Windows용으로 컴파일하는 CI 잡이 없습니다. 모듈을 `cfg(any(target_os = "windows", test))`로 게이트해 센서 매핑, 범위 가드, 필드 적용이 모두 Linux 테스트 러너에서 실행됩니다. 신규 테스트 34개.

| 게이트 | 결과 |
|--------|------|
| `cargo fmt --check` | 통과 |
| `cargo clippy --all-targets -- -D warnings` | 통과 |
| `cargo test` | 3162 통과, 0 실패 (이전 `main`은 3128) |
| `cargo xwin check --target x86_64-pc-windows-msvc` | 통과, 경고 0 |
| `cargo xwin clippy --target x86_64-pc-windows-msvc -- -D warnings` | 이 변경분에 대해 통과 |

레이아웃은 `ADLSingleSensorData`(8바이트, 4정렬)와 `ADLPMLogDataOutput`(2052바이트)에 대한 컴파일 타임 단언, 그리고 센서 배열이 오프셋 4부터 8바이트 레코드 단위로 실제로 진행하는지 단언하는 테스트로 고정했습니다. 이 단언들은 이 ABI가 가질 수 있는 유일한 자동 검사이며, 그래서 장식이 아니라 거기에 있습니다.

## 5. 보안 관점

DLL은 맨 이름이 아니라 절대 `System32` 경로에서 로드하며, 이는 `windows_temp/amd_ryzen.rs`에 이미 문서화된 DLL 하이재킹 대응 방침과 같습니다. import 라이브러리를 참조하지 않으므로 실행 파일의 import 테이블에 `atiadlxx` 항목이 없습니다. 이는 #345가 Linux에서 요구하는 것과 의도적으로 같은 형태입니다. Linux에서는 `libdrm` 부재가 `main` 실행 전 로더 오류이지 완화 가능한 조건이 아닙니다.
