# 기술 보고서: PR #424 - M1 Ultra 에너지 채널 검증

**날짜**: 2026-09-20
**상태**: 완료
**언어**: Rust, Markdown
**위험도**: 낮음

---

## 요약

#410이 세운 Apple Silicon 에너지 모델 규칙을 다이가 여럿인 칩에서 처음으로 실물 검증한다. 대상은 M1 Ultra(Mac13,2, macOS 27.0 26A428)이고, 결과는 채널 321개짜리 인벤토리 픽스처와 테스트 15개로 고정했다. 열려 있던 질문들은 측정으로 답이 났다. `DIE_<n>_` 접두사는 CPU 채널에만 붙으므로 다이 접두사 규칙을 새로 만들 필요가 없었고, `GPU0_0`은 다이 0이 아니라 SRAM을 뺀 GPU 전체로 드러나 GPU 폴백을 그 이름 모양까지 확장했으며, `sum_rails`에는 샘플에 존재하는 가장 덜 구체적인 채널 계열만 레일에 들어가게 하는 가드를 넣어 다이별 합이 패키지 총합에 더해질 수 없게 했다. 진단 코드는 자체 모듈로 옮기고, 에너지 비교와 함께 SMC 온도 키 인벤토리도 출력한다.

---

## 1. 문제 정의

### 1.1 배경

#410(PR #412)은 Apple Silicon 전력을 폴링 구간이 아니라 각 `Energy Model` 채널이 가진 드라이버 게시 타임스탬프로 계산하고, `classify_energy_channel`에서 채널을 정확한 이름으로 매칭한다. 그런데 이 모든 것이 칩 하나, M5 Max에서만 검증되었다. 채널 364개짜리 그 인벤토리가, 모든 Apple Silicon 파트를 덮도록 쓰인 규칙의 유일한 기록 증거였다.

Ultra는 다이가 둘이고, 두 다이짜리 패키지가 채널 이름을 어떻게 짓는지는 M5 Max 인벤토리 어디에도 없다. GitHub macOS 러너는 IOReport가 없는 가상 머신이므로, 이 질문은 실물 하드웨어에서만 답할 수 있었다.

### 1.2 기존 문제

- **다이가 여럿인 패키지의 채널 이름을 모른다**: GPU, ANE, DRAM 블록이 CPU처럼 `DIE_<n>_` 접두사를 쓰는지는 추측이었고, 분류기가 놓친 레일 채널은 구독조차 되지 않으므로 조용히 0 W로 읽힌다.
- **잠복한 중복 계산**: `DIE_<n>_CPU Energy` 옆에 패키지 `CPU Energy`가 있으면 두 규칙에 모두 걸려 두 번 합산된다. `multi_die_rails_are_summed`는 다이별 채널만 존재한다고 가정하고 있었다.
- **두 번째 칩에서 검증되지 않은 게시 주기**: 묶음 게시 동작, 짧은 분할 꼬리, 타임스탬프 폴백이 모두 M5 Max 관찰이었다.
- **칩마다 다른 SMC 집계를 볼 방법이 없었다**: 온도 게터는 정적 키 목록을 우선하고 정적 키가 하나도 정상 범위로 읽히지 않을 때만 탐색으로 넘어간다. 즉 레일이 어느 경로를 타는지는 칩마다 다른데, 진단은 그중 무엇도 출력하지 않았다.

### 1.3 위험 평가

| 위험 | 영향 | 발생 가능성 |
|------|------|-------------|
| 다이가 여럿인 칩의 레일 채널이 아무 규칙에도 걸리지 않아 구독되지 않고 0 W로 보고된다 | 높음 | 중간 |
| 패키지 채널과 다이별 채널이 함께 합산되어 레일이 약 2배로 부푼다 | 높음 | 낮음 |
| 칩 하나에서 일반화한 규칙을 검증된 것처럼 출하한다 | 중간 | 높음 |
| 온도 집계가 칩마다 같다고 가정하지만 실제로는 다르다 | 낮음 | 높음 |

## 2. 기술적 결정

### 2.1 GPU, ANE, DRAM에 `DIE_<n>_` 규칙을 새로 넣지 않는다

M1 Ultra 인벤토리가 취향이 아니라 증거로 결론을 낸다. 채널 321개 가운데 `DIE_<n>_` 접두사를 가진 것은 34개뿐이고 전부 CPU 채널이다. 클러스터, 코어별 채널, `_CPM`, 그리고 다이마다 하나씩인 `DIE_<n>_CPU Energy`다. 나머지 블록은 접두사 대신 접미사로 다이를 표시한다. `ANE0_0`과 `ANE0_1`, `DRAM0_0`과 `DRAM0_1`, 그리고 `ISP`, `AVE`, `MSR`, `DCS`, `AMCC`도 같은 모양이다.

기록된 어느 칩에도 `DIE_<n>_` 형태의 GPU, ANE, DRAM 채널이 없으므로, 규칙을 추가한다는 것은 데이터 없이 매칭 규칙을 쓰는 일이 된다. 이 결정은 그것을 뒷받침하는 인벤토리와 함께 `energy.rs` 모듈 문서에 기록했다. #415의 수용 기준 4번이 요구한 형태다.

### 2.2 GPU 폴백을 `GPU<n>_<m>`까지 확장하고, 맨 `GPU`는 제외한다

M1 Ultra에는 `GPU Energy` 옆에 `GPU0_0` 하나(그리고 `GPU SRAM0_0`)가 있다. 기존 규칙은 `GPU<n>`만 매칭했으므로 `GPU0_0`은 아무 레일에도 분류되지 않았고 구독조차 되지 않았다.

`GPU0_0`이 "다이 0"인지 "GPU 전체"인지가, `GPU Energy`가 없는 칩이 GPU 전력을 절반으로 읽을지 말지를 가른다. 비교 실행이 답을 준다.

| 실행 | `GPU0_0` / `GPU Energy` | `(GPU0_0 + GPU SRAM0_0)` / `GPU Energy` |
|---|---|---|
| 공식 유휴, 29.292 s 구간 | 0.963 | 0.996 |
| 공식 부하, 29.278 s 구간 | 0.938 | 0.967 |
| 변경 후 실행, 30.066 s 구간 | 0.973 | 1.004 |

다이 0만 담은 채널이라면 0.5 근처로 읽혔을 것이다. `GPU0_0`은 SRAM을 뺀 GPU 전체이므로 그 이름 모양까지 폴백을 확장해도 안전하고, 여기로 폴백하는 칩은 약 3 % 낮게 읽게 된다. 맨 `GPU`는 무엇이 들었는지 보여 준 데이터가 없으므로 명시적으로 제외한다.

M1 Ultra 자신에게는 이 확장이 어떤 측정값도 바꾸지 않는다. `GPU0_0`은 구독되고 추적되지만 `GPU Energy`가 존재하므로 GPU 레일은 여전히 `GPU Energy` 하나다.

### 2.3 `sum_rails`는 패키지 채널이나 다이별 채널 중 하나만 센다

둘 다 가진 칩은 없을 것이라고 믿는 대신, 합산 단계가 모든 레일에서 이를 강제한다. 채널을 이름이 얼마나 구체적인지에 따라 묶고, 샘플에 존재하는 가장 덜 구체적인 계열만 레일에 들어간다.

```rust
struct Families([Option<f64>; 3]);
// 0: 패키지 이름 (`CPU Energy`, `ANE`, `DRAM`)
// 1: 번호 블록 (`GPU<n>`, `ANE<n>`, `DRAM<n>`; CPU는 `DIE_<n>_CPU Energy`)
// 2: 다이 접미사 (`GPU<n>_<m>`, `ANE<n>_<m>`, `DRAM<n>_<m>`)
```

패키지 `CPU Energy`는 `DIE_<n>_CPU Energy`를 덮고, `GPU Energy`가 없으면 폴백은 `GPU<n>_<m>`보다 `GPU<n>`을 먼저 쓰며, ANE와 DRAM은 맨 `ANE` / `DRAM`, 그다음 `ANE<n>` / `DRAM<n>`, 마지막으로 다이 접미사 순이다.

모든 채널은 여전히 분류되므로 구독 필터와 추적기는 전부를 유지하고, 결정은 샘플 단위로 합산 시점에 내려진다. 기록된 어느 칩도 이 가드를 건드리지 않는다. M5 Max와 M1 Ultra 모두 레일마다 계열이 정확히 하나씩이라 둘 다 이전과 똑같이 읽는다. 가드는 아직 아무도 기록하지 않은 다이 여러 개짜리 칩, 이를테면 M2 Ultra와 M3 Ultra를 위한 것이다.

### 2.4 진단은 추적 채널이 아니라 후보를 비교한다

기존 진단은 필터링된 구독을 샘플링했으므로, 분류기가 놓친 레일 채널은 정작 그것을 찾으려는 실행에서 보이지 않았다. 이제 32 s 동안 필터 없는 `Energy Model` 구독을 열고, 공통 게시 구간에 걸쳐 모든 GPU, ANE, DRAM, `CPU Energy` 후보를 비교한다. 줄, 와트, 채널별 게시 구간, 타임스탬프 이상, 그리고 위의 비율을 출력한다. `GPU0_0`은 어떤 규칙이 받아들이기 전에 이렇게 측정되었다.

## 3. 구현 내용

### 3.1 픽스처와 테스트

`tests/fixtures/ioreport/m1_ultra_energy_model.tsv`는 321개 채널 전부를 열거 순서대로 `name<TAB>unit`으로 담고, 헤더에 칩, 모델 식별자, macOS 빌드, 캡처 날짜를 M5 Max 픽스처와 같은 형식으로 적는다. 필터링된 구독을 샘플링한 것이 아니라 `IOReportCopyChannelsInGroup`으로 열거했고, 두 공식 실행이 바이트 단위로 같은 결과를 냈다.

분류 테스트는 321개 중 정확히 8개만 레일을 먹인다는 것을 고정한다.

```
ANE0_0, ANE0_1, DIE_0_CPU Energy, DIE_1_CPU Energy,
DRAM0_0, DRAM0_1, GPU Energy, GPU0_0
```

같은 목록을 `channel_filter.rs`에서 필터 쪽으로도 단언한다. 분류기 변경이 구독 대상을 조용히 바꾸지 못하게 막는 장치다. 나머지 313개는 다이별로 반복되는 같은 계열들, `GPU SRAM0_0`, 그리고 끝의 ` Energy`가 어느 규칙에도 걸리지 않는 `apciec<n> Energy`와 `PCIe Port <n> Energy` 채널이다.

인벤토리 특성 하나는 별도 테스트가 필요했다. `DTL` 이름 130개(`ECPUDTL*`, `PCPUDTL*`, `PCPU1DTL*`)가 각각 두 번씩 나오는데 둘을 구분할 접두사가 없다. `EnergyTracker`는 채널을 이름으로 키잉하므로, 중복된 이름이 분류되면 키가 모호해진다. 그중 아무것도 분류되지 않고, 테스트가 그것을 고정한다.

### 3.2 게시 주기

M1 Ultra도 M5 Max처럼 mJ 채널을 한꺼번에 게시하지만, 약 2.1 s마다 두 번씩 고르지 않은 간격으로 내보내고 그 분할 비율이 흔들린다. 한 32 s 실행에서는 0.75~0.91 s와 1.19~1.32 s가 번갈아 나왔고, 다른 실행에서는 1.69 + 0.46 s에서 0.97 + 1.14 s로 옮겨 갔다. 짧은 분할 꼬리를 제쳐 두면, 모든 게시는 두 번 앞선 게시로부터 유휴 시 2.03~2.13 s, 부하 시 2.02~2.20 s 뒤에 왔다. `GPU Energy`는 훨씬 짧은 110~246 ms 구간으로 게시한다.

각 게시의 에너지는 그 게시 자신의 구간을 따른다. 설계 전체가 여기에 걸려 있다. `DRAM0_0`은 유휴 실행에서 출력된 모든 구간(815~1295 ms)에 걸쳐 1.75~1.83 W를, 부하에서는 모든 구간(416~1690 ms)에 걸쳐 2.00~2.20 W를 읽었다. `MIN_PUBLICATION_SPAN_NS`는 50 ms 그대로다. M1 Ultra의 분할 꼬리는 12~29 ms이고, 샘플이 다음 게시 직전에 떨어졌을 때 `GPU Energy`가 에너지 없이 스탬프만 6~12 ms 움직인 경우도 있었는데, 기존 임계값이 둘 다 다음 구간으로 접어 넣는다.

### 3.3 SMC 온도 키 인벤토리

진단은 이제 어떤 정적 키가 존재하고 정상 범위로 읽히는지, 탐색이 키를 몇 개 찾는지, 각 레일이 어느 경로를 타는지를 게터가 쓰는 바로 그 키 목록과 범위로 출력한다. `smc.rs`는 네 곳에 흩어져 있던 리터럴 대신 단일 출처 상수(`CPU_STATIC_TEMP_KEYS`, `GPU_STATIC_TEMP_KEYS`, `PLAUSIBLE_TEMP_C`)를 쓰도록 정리했다. 집계 방식은 그대로다.

M1 Ultra 결과는 두 칩이 얼마나 다를 수 있는지 보여 준다.

| | M1 Ultra | M5 Max |
|---|---|---|
| 존재하는 정적 CPU 키 | 8개 중 6개 (`TC0P`, `TC0D` 없음) | 8개 중 0개 |
| 존재하는 정적 GPU 키 | 4개 중 1개 (`Tg0j`) | 4개 중 1개 (`Tg0j`) |
| 탐색된 CPU 키 | 86 | 23 |
| 탐색된 GPU 키 | 16 | 84 |
| CPU 온도 경로 | 정적, 6개 평균 | 탐색, 23개 평균 |
| GPU 온도 경로 | 정적, 센서 하나 | 정적, 센서 하나 |

유휴 실행에서 `get_cpu_temperature`는 59.06 C, `get_gpu_temperature`는 51.14 C를 돌려주었고, 부하에서는 CPU가 65.50 C였다. `MAX_CPU_TEMP_KEYS` 폭주 방지 주석은 실측값 86으로 갱신했다.

### 3.4 모듈 구성

진단은 `ioreport.rs`에서 `ioreport/diagnostics.rs`로 옮겼고, 후보 비교는 `ioreport/energy_comparison.rs`, SMC 키 보고는 `smc/temperature_report.rs`에 들어갔다. `ioreport.rs`는 112줄이 빠지고 모듈 문서에 M1 Ultra 게시 주기가 들어왔다.

## 4. 배운 점

### 4.1 이름 모양은 의미가 아니다

`GPU0_0`은 "GPU 블록 0, 다이 0"처럼 읽히고, 다이가 둘인 패키지에서는 GPU의 절반을 덮는다고 추론하는 것이 자연스럽다. 측정은 반대를 말한다. SRAM을 뺀 GPU 전체이고, 그래서 변경 후 실행에서 `(GPU0_0 + GPU SRAM0_0)`이 `GPU Energy`의 0.4 % 안쪽에 떨어진다. 폴백 규칙을 어떤 이름 모양까지 넓히는 일은 그 채널이 무엇을 담았는지에 대한 주장이고, 공통 구간의 나란한 비교만이 그 주장을 뒷받침할 수 있다.

### 4.2 필터링된 진단은 필터가 버린 것을 찾을 수 없다

분류기가 곧 구독 술어였으므로, 진단은 분류기가 이미 받아들인 채널만 정확히 샘플링했다. 놓친 레일 채널은, 놓친 레일 채널을 찾으려고 만든 도구에 보이지 않았다. 검증 도구는 자기가 검증하는 필터 바깥에 있어야 한다.

### 4.3 칩이 그 조합을 만들기 전에 먼저 막는다

기록된 어느 칩도 같은 레일에 패키지 채널과 다이별 채널을 함께 갖고 있지 않으므로, 중복 계산 가드는 현재 어떤 측정값도 바꾸지 않고 지금 구할 수 있는 하드웨어로는 구동할 수도 없다. 그래도 넣을 값어치가 있었다. 실패 양상이 전력 수치의 조용한 2배이고, 대안은 아직 아무도 갖지 못한 칩에서 그것을 발견하는 것이기 때문이다. 정직한 형태는 그것을 그대로 적는 것이다. 모듈 문서는 기록된 어느 칩도 이 가드를 건드리지 않으며 M2 Ultra와 M3 Ultra 부류를 위한 것이라고 분명히 말한다.

## 6. 검증과 후속

### 완료한 검증

- `cargo test --lib device::macos_native`: 107개 통과, 하드웨어 진단은 ignored.
- `cargo test --test user_facing_text_test`, `cargo clippy --lib --tests -- -D warnings`, `cargo fmt --check`, 그리고 프리커밋 훅의 `cargo clippy --all-targets --all-features -- -D warnings`.
- M1 Ultra에서 `ioreport_energy_diagnostics` 공식 실행 2회. 바쁜 공용 호스트에서의 유휴 상태와 `yes` 4개 부하 상태이며 둘 다 PR에 첨부했다. 공통 구간의 레일 합: 유휴 cpu 5.940 W, dram 3.644 W, gpu 0.038 W, ane 0.000 W. 부하 cpu 17.012 W, dram 3.972 W, gpu 0.081 W, ane 0.049 W. 두 실행 모두 추적 채널에 타임스탬프 이상이 없었다.
- `833cc55`에서의 릴리스 부하 점검: `yes` 4개 부하 아래 `all-smi api --port 19090 --interval 1`, 3 s 워밍업 후 1초 간격 20 샘플. CPU 전력 14.09~15.49 W, 평균 14.76, 0 W 샘플 없음. 같은 구간에 진단을 함께 돌려 272틱 동안 추적기 CPU 레일 평균 14.95 W, 0틱 없음을 읽었고, 30.1 s 공통 구간에서 `DIE_<n>_CPU Energy` 두 채널의 합은 14.84 W였다. #415의 수용 기준 3번에 해당한다.
- M5 Max 픽스처와 테스트가 수정 없이 통과한다. #415가 분류기 변경에 건 제약이다.

### 검증하지 못한 것

- GPU가 실제로 바쁜 상태에서의 `GPU0_0` 대 `GPU Energy` 비교. 공식 실행 둘 다 GPU가 38~81 mW였다. 첨부하지 않은 탐색 실행에서만 약 7.5 W로 활동했고, 단독 0.980, `GPU SRAM0_0`을 더하면 1.000이었다.
- 부하 실행의 0.938은 6.2 % 차이로, "몇 퍼센트 이내"라는 엄격한 해석을 벗어난다. 리뷰는 이를 MEDIUM 항목으로 열어 두었다. SRAM 분해가 다이 0 전용 채널 가능성을 배제하고, GPU 활동 증거는 탐색적이라고 명시했다.
- 실물 하드웨어에서의 패키지 우선 가드. 한 레일에 두 계열을 모두 가진 기록된 칩이 없다.
- `GPU Energy` 스탬프가 완전히 얼어붙는 경우는 200 ms 간격으로 샘플링하며 GPU가 8 W 근처였던 첨부하지 않은 탐색 실행에서만 나왔고, 공식 실행에는 없었다. 기존 hold 테스트가 덮는다.
- 나머지 모든 칩: M1, M1 Pro, M1 Max, M2, M2 Pro, M2 Max, M2 Ultra, M3, M3 Pro, M3 Max, M3 Ultra, M4, M4 Pro, M4 Max, M5, M5 Pro. Intel Mac은 범위 밖이다.

### 남은 제약

- `energy.rs`: 닫힌 구간이 없거나 오래된 패키지 채널은 0 W로 합산되어 살아 있는 다이별 측정값을 가린다. 의도된 동작이고 테스트로 고정되어 있으며, 두 계열을 모두 가진 칩에서만 도달 가능하다.
- `diagnostics.rs`: 필터 없는 구독과 그 딕셔너리가 해제되지 않는다. 기존 `IOReport::new` 패턴을 따른 것이고 테스트 전용 코드다.
- `smc/temperature_report.rs`는 `"SMC key not found"` 문자열을 리터럴로 비교하므로, 메시지가 바뀌면 없는 키를 읽기 실패로 보고하게 된다.
- #415가 범위 밖으로 둔 것이고 여기서도 그대로다: 키 인벤토리가 확보된 뒤의 온도 집계 방식, 그리고 #414가 다루는 macOS IOReport와 SMC 읽기 주기.
