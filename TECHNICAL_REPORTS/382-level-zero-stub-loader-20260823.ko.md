## 요약

PR #382는 Intel Level Zero 백엔드에 결정적이고 하드웨어 독립적인 통합 테스트 커버리지를 추가했습니다. CI가 Intel 벤더 헤더로 테스트 전용 C 로더를 컴파일하고, 격리된 단일 테스트 단계에서 시스템 로더보다 먼저 탐색되도록 한 뒤, 공개 Rust API를 통해 백엔드를 구동합니다. 이에 따라 Intel GPU가 없는 환경에서도 ABI 레이아웃, 장치 열거, BDF 매핑, count-then-fill 처리, 메트릭 변환, 델타 계산 및 메트릭 패밀리별 실패 격리를 검증합니다.

최종 리뷰에서는 원래 픽스처의 두 가지 누락을 발견했습니다. Rust 통합 테스트가 병렬 실행될 때 가변 전역 카운터가 경쟁할 수 있었고, 음수 경로용 장치가 실제 Sysman 오류가 아니라 성공과 빈 결과를 반환했습니다. 픽스처는 이제 relaxed C atomic을 사용하며, Device B는 전력 도메인 열거에서 `ZE_RESULT_ERROR_UNSUPPORTED_FEATURE`를 반환합니다. CI에서 무장된 다섯 테스트와 정확한 clippy 게이트가 모두 통과했습니다. PR은 `89cd907`로 squash merge되었고 이슈 #379는 자동 종료되었습니다.

## 1. 문제 정의

기존 Level Zero 로더 검사는 `dlopen`과 심볼 해석까지만 수행했습니다. Intel GPU가 없는 러너에서 이후 `zeInit` 실패는 정상이나, 그 결과 다음 프로덕션 경로에는 실행 가능한 CI 커버리지가 없었습니다.

- 장치 열거 및 BDF 매핑.
- 핸들 수 제한과 실제 채움 수에 따른 축소를 포함한 count-then-buffer 규약.
- 실제 벤더 ABI를 기준으로 한 C/Rust FFI 필드 순서.
- 델타 기반 엔진 사용률 및 전력 계산.
- 온도, 메모리, 주파수, 팬의 시점 메트릭 갱신.
- 하나의 Sysman 메트릭 패밀리가 실패할 때의 격리.

Rust 내부 레이아웃 단언은 크기 불일치를 탐지할 수 있지만, 구조체와 단언이 동일한 전사 오류를 반복하면 같은 타입의 두 필드가 뒤바뀐 문제를 신뢰성 있게 잡을 수 없습니다. 따라서 Intel 자체 헤더로 컴파일된 독립적인 C 측 검증이 필요했습니다.

## 3. 기술적 결정

### 3.1 벤더 헤더를 기준으로 컴파일

C 픽스처는 Rust 측 선언을 다시 옮겨 적지 않고 Intel Level Zero 헤더를 직접 포함합니다. 벤더가 정의한 구조체를 통해 기록한 값을 프로젝트의 `#[repr(C)]` Rust 구조체로 읽습니다. 따라서 크기만 확인하는 단언으로는 놓칠 수 있는 동일 크기 필드의 순서 및 오프셋 오류를 탐지할 수 있습니다.

검증용 커밋에서는 `zes_freq_state_t`의 두 필드를 의도적으로 맞바꿨습니다. CI 실행 `32623903057`은 `actual`이 `2100` 대신 `1200`을 읽으며 실패했고, 테스트가 이 결함 유형에 실제로 도달함을 증명했습니다. 해당 변경은 머지 전에 되돌렸습니다.

### 3.2 테스트 로더를 프로덕션 설정에서 배제

픽스처는 `libze_loader.so.1`로 빌드되며, 기존 로더는 이미 이 SONAME을 그대로 엽니다. 전용 통합 테스트 단계에서만 `LD_LIBRARY_PATH`를 변경하므로 일반 CI 단계와 배포 바이너리는 표준 로더 탐색 동작을 유지합니다.

임의 로더 경로를 받는 애플리케이션 환경 변수는 의도적으로 추가하지 않았습니다. 픽스처를 위한 프로덕션 분기, 런타임 오버라이드, 바이너리 페이로드 또는 릴리스 산출물은 없습니다.

### 3.3 별도 통합 테스트 프로세스 사용

Level Zero 런타임은 프로세스 전역 `OnceCell`에 저장됩니다. 단위 테스트 바이너리 안에서 실행하면 먼저 초기화한 테스트가 실제 로더와 스텁 로더 중 하나를 영구 선택할 수 있습니다. 전용 통합 테스트 타깃으로 프로세스를 분리하여 로더 선택을 결정적으로 유지했습니다.

### 3.4 픽스처의 가변 상태를 atomic으로 처리

Rust는 기본적으로 테스트를 병렬 실행합니다. 일반 C 전역 카운터는 동기화되지 않은 읽기와 쓰기를 허용하여 데이터 레이스와 정의되지 않은 동작을 일으킬 수 있습니다. 최종 픽스처는 `_Atomic uint64_t` 및 relaxed `atomic_fetch_add_explicit` 연산을 사용합니다. 이 테스트에는 변수 간 순서 보장이 아니라 증가 연산의 불가분성만 필요하므로 relaxed 순서로 충분합니다.

### 3.5 실제 메트릭 패밀리 실패 모델링

Device B는 이제 전력 도메인 열거에서 `ZE_RESULT_ERROR_UNSUPPORTED_FEATURE`를 반환합니다. 테스트는 장치를 두 번 갱신하여 렌더 사용률은 정확히 10%의 최신 값을 유지하고 전력만 사용할 수 없음을 증명합니다. 한 패밀리의 오류가 관련 없는 메트릭을 억제하지 않음을 검증합니다.

## 4. 구현 상세

픽스처는 백엔드가 해석하는 모든 심볼을 내보냅니다. 핵심 초기화 및 장치 함수, `zesInit`, 엔진·전력·온도·메모리·주파수·팬 패밀리를 합쳐 23개입니다. 각 값은 서로 명확히 구분되도록 선택하여 오프셋 오류가 그럴듯한 값이 아니라 확실히 잘못된 값을 만들도록 했습니다.

카운터는 시계나 난수 없이 고정 증분으로 진행됩니다. 따라서 두 번째 샘플의 기대값은 compute 25%, render 10%, 전력 45 W로 정확합니다. 다른 장치는 카운트 질의에서 4,096개 핸들을 보고하지만 실제로 하나만 채워 최대 핸들 제한과 실제 채움 수에 따른 축소를 함께 검증합니다.

다섯 통합 테스트의 범위는 다음과 같습니다.

1. 정렬된 BDF 열거의 종단 간 검증.
2. 엔진 사용률 및 전력 델타의 정확한 값.
3. 시점 메트릭 패밀리가 `GpuInfo`를 채우는 동작.
4. 핸들 카운트 경계와 실패하는 패밀리의 격리.
5. 알 수 없는 BDF가 바인딩되지 않는 동작.

CI는 테스트를 명시적으로 무장합니다. 단언이 통과한 뒤에만 성공 마커를 출력하고 워크플로가 다섯 마커를 요구하므로, 지원하지 않는 플랫폼이나 실수로 건너뛴 테스트 본문이 성공으로 보이는 일을 방지합니다.

## 5. 리뷰 및 보강

최종 리뷰에서는 정확성, 보안, 성능, ABI 경계, 테스트 병렬 실행 및 CI 도달성을 점검했습니다. 커밋 `2443b4e`(`test: make the Level Zero stub concurrency-safe`)에 앞서 설명한 atomic 카운터 및 실제 오류 경로 수정을 추가했습니다.

남아 있는 CRITICAL 또는 HIGH 보안 문제는 없습니다. 로더 인터포지션은 단일 CI 단계로 제한되며, 배포되는 애플리케이션 설정을 통해 픽스처에 접근할 수 없습니다. 프로덕션 런타임 성능 영향은 없습니다. relaxed atomic의 미미한 비용은 테스트 픽스처에만 발생합니다.
