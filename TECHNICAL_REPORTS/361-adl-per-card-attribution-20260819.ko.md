# 기술 보고서: PR #361 - 다중 GPU AMD Windows 호스트에서 ADL 텔레메트리 카드별 귀속

**일자**: 2026-08-19  
**상태**: 코드 경로 기준 완료, 레이아웃은 실하드웨어 미검증 (6절 참조)  
**관련 항목**: PR #361, 이슈 #353, PR #349에서 등록한 후속 / 이슈 #370  
**위험 수준**: 높음 (비공개 드라이버가 쓰는 1572바이트 구조체를 손으로 전사, CI가 컴파일하지 않는 타겟)

---

## 요약

PR #361은 AMD 공개 `adl_structures.h`에서 도출한 Windows 레이아웃으로 `ffi.rs`에 `AdapterInfo`를 선언하고, ADL 어댑터 행을 PCI bus/device/function으로 물리 카드별로 묶은 다음, `strPNPString`을 WMI `PNPDeviceID`와 대조해 카드를 리더의 GPU에 매칭합니다. 이로써 #349가 걸어 둔 단일 AMD GPU 제약이 풀리고, 가장 흔한 다중 AMD 구성인 Ryzen APU + Radeon dGPU 노트북이 아무것도 못 받던 상태에서 온도, 전력, 팬, 클럭을 받게 됩니다.

이 PR은 네 커밋으로 들어갔습니다. 최초 구현, 그리고 검증 자체의 결함, 드라이버 이상 상황 다섯 가지, `cfg(target_os = "windows")` 뒤의 테스트 공백을 각각 닫은 세 차례 하드닝입니다.

---

## 1. 문제 정의

`AdapterInfo` 없이는 ADL 어댑터 인덱스를 물리 카드에 묶을 수 없고, 카드 하나가 디스플레이 출력마다 하나씩 여러 인덱스를 노출하며 전부 동일한 텔레메트리를 보고합니다. 그래서 #349는 보강 전에 AMD GPU가 정확히 하나일 것을 요구했고, 이는 정직한 답이지만 다중 GPU 경우를 DXGI/PDH 기준선만 남긴 채로 둡니다.

어려운 부분은 구조체입니다. ADL은 **자기** `sizeof`를 기준으로 쓰므로 레이아웃 실수는 깔끔한 실패가 아니라 호출자 버퍼 오버플로가 되며, CI에서 이 코드를 컴파일하는 것이 없습니다.

이슈 본문에 대한 기록: 이슈에 적힌 1568바이트 수치는 틀렸습니다. 그 공식이 `iAdapterIndex`를 빠뜨립니다. 올바른 레이아웃은 int 9개에 `char[256]` 배열 6개, 패딩 없이 1572바이트입니다.

## 3. 기술적 선택과 그 이유

### 3.1 컴파일 타임 단언으로는 충분할 수 없으므로 런타임 검증

컴파일 타임 크기/오프셋 단언은 전사를 자기 자신에 대해 고정합니다. 내부적으로는 일관되지만 드라이버에 대해서는 틀린 전사를 잡지 못합니다.

그래서 런타임 검증을 추가했습니다. 모든 행의 NUL 종료 ASCII 문자열 필드 네 개가 읽을 수 있는 텍스트여야 하고, 채워진 경우 `iSize`가 `size_of`와 일치해야 하며, **행 단위로** 검사하므로 첫 행이 파싱되더라도 잘못된 stride는 두 번째 항목에서 잡힙니다. 검사 실패, 매칭 실패, 진입점 부재, 호출 실패는 모두 귀속을 거절하고 DXGI/PDH 기준선을 유지합니다. 이는 `match_adapter`에 대해 #346 리뷰가 도달한 결론입니다.

`plan_attribution`은 `SoleGpu`, `PerCard`, `Decline`을 반환합니다. 단일 GPU 호스트는 `AdapterInfo`를 조회하지 않고 #353 이전 동작을 유지하며, 이는 회귀 테스트로 고정했습니다.

### 3.2 검증에 구멍이 있었고, 두 번째 커밋이 그것을 닫았다

`AdapterInfoArray::for_count`는 버퍼를 0으로 채운 행으로 사전 초기화하는데, **`looks_sane`의 모든 분기가 그 0 행으로 개별적으로 충족**됐습니다. `iSize` 0은 명시적으로 허용되고, `iAdapterIndex` 0은 범위 안이며, 각 문자열 필드는 오프셋 0의 NUL인데 `adl_string`은 이를 쓰레기가 아니라 빈 문자열로 문서화합니다. 따라서 ADL이 손대지 않은 버퍼가 유효한 빈 어댑터 표로서 레이아웃 검증을 통과했습니다.

이는 이 전사에 실제로 돌 유일한 검증을 속 빈 것으로 만들었습니다. 실제 `sizeof(AdapterInfo)`가 선언한 1572보다 크면 ADL은 행 수를 `iInputSize / sizeof`로 계산해 요청보다 적은 행을 쓰고 꼬리를 비워 둡니다. 아무것도 깨지지 않으므로 행별 문자열 검사가 통과하고, 잘못된 stride가 두 번째 행에서 잡힌다는 문서화된 보장이 아무것도 깨지지 않는 바로 그 방향에서 성립하지 않았습니다. 실제 다중 GPU 호스트가 레이아웃을 확인하거나 반증하는 수단인 `amd.adl.adapters` 진단 검사가 드라이버가 채운 적 없는 행들에 대해 PASS를 보고했을 것입니다.

이제 `is_blank`가 행을 사전 초기화된 0과 비교하고 `looks_sane`이 그것에 대해 실패합니다. 빈 행은 어떤 GPU와도 매칭되지 않는 빈 PNP 문자열로 묶이므로 귀속 자체는 위험한 적이 없었고, 따라서 이것은 오귀속 수정이 아니라 검증의 복원입니다.

### 3.3 세 번째 커밋에서 닫은 드라이버 이상 상황 다섯 가지

보안/성능 리뷰는 새 FFI 자체에서 메모리 안전성 결함을 찾지 못했습니다. 광고된 `iInputSize`는 항상 할당보다 엄격히 작고, 호출 전 버퍼가 0으로 채워지므로 초기화되지 않은 행을 읽는 일이 없으며, 모든 필드 타입이 드라이버가 쓸 수 있는 어떤 비트 패턴도 받아들이고, 호출을 가로질러 살아 있는 Rust 참조가 없으며, 임의의 드라이버 바이트에 패닉하는 경로가 없습니다. 아래 다섯 수정은 그 핵심 주변의 낮은 심각도 공백을 닫으며, 전부 이 모듈이 이미 택한 방향(추측 대신 거절)입니다.

| 수정 | 막는 것 |
|------|---------|
| `group_by_card`가 서로 다른 비어 있지 않은 PNP 경로 두 개를 가진 그룹을 병합 대신 폐기 | bus/device/function을 채우지 않는 드라이버가 모든 카드를 한 그룹으로 뭉개고, `augment`는 PMLog에 응답하는 그룹의 첫 인덱스를 샘플링하므로 한 카드의 온도/전력/팬이 다른 GPU로 보고될 수 있음 |
| `scan_for_capable_adapter`가 드라이버의 어댑터 개수를 `MAX_ADAPTER_ROWS`로 클램프 | 이 스캔은 인덱스마다 `ADL2_Overdrive_Caps` 호출 하나와 경우에 따라 8 KB를 할당하는 PMLog 읽기 하나를, 프로세스 전역 런타임 락을 쥔 채로 수행하므로 쓰레기 개수가 모니터링 갱신 루프를 멈춰 세움 |
| `read_pmlog`가 포인터를 패딩 버퍼 전체에서 도출하고 캐스트로 좁힘 | `&raw mut buffer.output`은 그 필드의 2052바이트에만 유효해, 헤드룸이 흡수하려고 존재하는 바로 그 초과 쓰기에 대해 헤드룸이 범위 밖에 놓임 |
| `AdapterInfoArray::input_size`가 절삭 `as`가 아닌 검사된 변환 | 할당을 넘어서면 비공개 드라이버 내부의 버퍼 오버플로가 되는 유일한 수치이므로 조용한 랩어라운드로 도달 가능해서는 안 됨 |
| 진단 검사가 실패한 검증이 어느 방향을 가리키는지 명시 | 빈 행은 선언한 구조체가 드라이버 것보다 크다는 뜻이고, 깨진 문자열은 반대 오류. 둘은 정반대 교정을 요구함 |

빈 형제 행은 여전히 backfill되고, 대소문자 차이는 여전히 충돌이 아닙니다. WMI와 ADL이 대소문자에 합의하지 않기 때문입니다.

### 3.4 테스트 가능하도록 로직을 `cfg(target_os = "windows")` 밖으로

클램프된 스캔 루프, `plausible_adapter_count` 거부 경로, 진단 검사의 blank 대 garbled 실패 메시지에는 자동 커버리지가 없었습니다. 모든 호출자가 `cfg(target_os = "windows")` 뒤에 있었고 이 저장소에는 Windows CI 잡이 없습니다.

네 번째 커밋은 `MAX_ADAPTER_ROWS`, plausible-count 검사, 스캔 클램프, 실패 형태 포매터를 플랫폼 독립 `adapters.rs`로 옮겼습니다. 모듈이 그룹화와 매칭에 이미 쓰던 것과 같은 분리이며, 이로써 산술과 메시지 로직이 미검증 상태로 배포되는 대신 Linux 테스트 러너에서 실행됩니다.

### 3.5 알려진 검증 공백 두 가지를 암묵이 아니라 소스에 기록

둘 다 `AdapterInfo::is_blank`와 `looks_sane`에 직접 문서화했습니다.

- 빈 행 거부는 일부 행을 정당하게 손대지 않는 드라이버에 대해 과하게 엄격할 수 있습니다. AMD 자체 SDK 샘플은 모든 행이 채워졌다고 가정하는 대신 `iPresent`로 필터링합니다.
- `looks_sane`은 구조체의 문자열 필드 6개 중 4개만 검사합니다. 나머지 둘은 `strPNPString`에 의해 전이적으로 고정되기 때문입니다.

둘 다 실하드웨어 증거가 나올 때까지 그대로 두었고, PR 본문에 어느 쪽이든 재검토를 정당화할 구체적인 덤프 형태를 적어 두었습니다.

## 5. 보안 관점

리뷰의 핵심 결론은 이 FFI 전체의 근간이 되는 주장이므로 다시 적어 둡니다. 광고된 `iInputSize`는 항상 할당보다 엄격히 작고, 호출 전 버퍼가 0으로 채워지며, 모든 필드 타입이 임의 비트 패턴을 받아들이고, 호출을 가로질러 살아 있는 Rust 참조가 없으며, 임의의 드라이버 바이트에 패닉하는 경로가 없습니다. 3.3의 모든 항목은 이 핵심의 수리가 아니라 그 주변의 방어입니다.

## 6. 결과 및 후속

- PR #361은 `f698b7e`로 `main`에 squash merge되었습니다.
- 레이아웃은 **실하드웨어 미검증** 상태입니다. all-smi를 Windows용으로 컴파일하는 CI가 없고 다중 AMD GPU 호스트도 확보되지 않아, 런타임 검증과 거절 폴백이 안전장치입니다.
- **이슈 #370은 열려 있습니다**: AMD GPU가 둘 이상인 Windows 호스트에서 카드별 ADL 귀속 확인. `priority:low`이지만 이 PR이 스스로 충족할 수 없는 수용 기준입니다.
- PR #371이 곧이어, 이 경로들이 동작함을 증명하려고 손으로 쓰고 되돌렸던 임시 프로브를 영구적인 `amd.adl.per_adapter` 진단 검사로 만들었습니다.
