## 요약

PR #313은 `update_homebrew_formula.yml`의 인젝션과 경로 순회 결함을 닫았지만, 잡의 전반적인 권한 노출에 관한 발견 일곱 가지는 의도적으로 남겨두었다. 탭 푸시 토큰이 디스크에 남는 문제, 필요 이상으로 넓은 `permissions:` 부여, 동시성 제어 부재, 페이지네이션 없는 에셋 목록 조회, 탭 작업 트리 안에 내려받는 아티팩트, 체크섬과 URL을 짝이 아니라 독립적으로 검증하는 문제, 설정되지 않은 `packaging` 환경이 그것이다. 이슈 #316이 이 일곱 가지를 추적했고, PR #318은 그 전부를 다룬다. 여섯 가지는 워크플로를 고쳐서, 한 가지는 아무것도 바꾸지 않겠다는 결정을 명시적으로 기록해서.

핵심은 탭 푸시 토큰을 이제 어떻게 범위 짓는가에 있다. 탭 클론은 익명이다(`lablup/homebrew-tap`은 공개 저장소이고, `brew tap lablup/tap`이 아무 자격 증명 없이 동작하려면 그래야 한다). 토큰은 잡 안에서 딱 한 곳, 마지막 `git push` 호출 하나의 환경 변수로만 닿는다. `$HOMEBREW_TAP_TOKEN`을 읽어 아무 데도 쓰지 않는 `credential.helper`를 통해서다. 이렇게 해서 git 푸시 토큰이 흔히 새는 네 경로가 전부 막힌다. 디스크(옛 코드는 토큰을 클론 URL에 넣었고, git은 이를 `.git/config`에 그대로 적었다), argv(`-c http.extraheader=...` 대안이었다면 `ps`로 보이고 어떤 `set -x` 추적에도 노출됐을 것이다), `set -x` 추적 자체(헬퍼 문자열이 홑따옴표로 감싸져 있어 bash는 `$HOMEBREW_TAP_TOKEN`이라는 이름 그대로를 git에 넘길 뿐 값을 확장하지 않고, xtrace는 git이 헬퍼 실행을 위해 띄우는 셸로는 전파되지 않는다), OS 키체인(`credential.helper`를 먼저 빈 값으로 리셋하면 러너의 기본 헬퍼가 빠져서, 인증에 성공한 뒤 그 사실을 나중에 저장해둘 곳 자체가 사라진다).

조사 과정에서 이슈 #316의 전제 하나는 성립하지 않는 것으로 드러났다. 이슈는 "최근 릴리스가 이미 에셋 28개를 갖고 있어 페이지네이션 없는 배열이 곧 잘릴 지경"이라고 근거를 댔다. 실제 개수는 18개였고, 임베디드 `assets` 배열의 잘림은 재현할 수 없었다. `electron/electron`(에셋 76개)과 `denoland/deno`(56개) 모두 이 워크플로가 읽는 같은 엔드포인트에서 전체 목록을 인라인으로 돌려주며, 이 프로젝트가 조만간 도달할 법한 개수 어디에서도 상한의 흔적이 없었다. 그래도 수정 자체는 유지했는데, 근거가 관측된 결함에서 문서화된 계약 논리로 바뀌었을 뿐이다. 임베디드 `assets` 배열은 `Link` 헤더도 없고 GitHub가 완전성을 보장한다고 문서화하지도 않은 반면, `/releases/{id}/assets`는 문서화되어 명시적으로 페이지네이션되는 컬렉션이다. 이 워크플로는 인텔 에셋의 부재를 능동적 결정(스탠자 갱신을 건너뛰거나, 다음 단계에서 버전 불일치 폼을라를 거부하거나)의 근거로 쓰므로, 그 결정을 문서화되지 않은 속성 위에 세우는 것 자체가 실제로 잘림이 발생했는지와 무관하게 제거할 가치가 있는 부분이다. 수정의 정당성이 애초 동기와 다른 이유로 성립하는 사례라 기록해 둘 만하다. 검증은 이번에 커밋된 `tests/homebrew-formula-workflow/`로 했다. 실제로 커밋된 워크플로 단계 본문에 대고 실행되는 어서션 69개를 다루고, 고의로 망가뜨린 워크플로 사본 세 개를 같은 하네스에 돌려 테스트가 공허하지 않음을 확인했다. 전체 규모는 워크플로 파일 1개와 새 테스트 하네스, 커밋 5개에 걸쳐 +1541/-25이고 #316을 닫는다.

## 1. 문제 정의

### 1.1 배경

`update_homebrew_formula.yml`은 GitHub Release마다 실행되어 그 릴리스의 아티팩트를 내려받고, 외부 저장소 `lablup/homebrew-tap`의 `Formula/all-smi.rb`를 새 체크섬과 URL로 다시 쓴다. PR #313(이슈 #308)은 여기에 인텔 맥 아티팩트를 서빙하도록 가르쳤고, 그 과정의 보안 리뷰에서 셸 인젝션 결함과 경로 순회 결함을 고쳤다. 같은 리뷰에서 잡의 권한 노출에 관한 발견 일곱 가지가 더 나왔는데, 인텔 아티팩트 기능 자체보다는 잡의 자격 증명이 얼마나 넓게 닿을 수 있느냐의 문제라 별도 PR로 의도적으로 미뤄졌다. 이슈 #316이 그 후속이다.

### 1.2 기존 문제점

- **문제 1 (토큰이 잡 전체 동안 디스크에 남음)**: 탭은 토큰이 박힌 URL, `https://x-access-token:<token>@github.com/lablup/homebrew-tap.git`로 클론됐다. Git은 이 URL을 `homebrew-tap/.git/config`에 `origin`으로 그대로 적어두므로, 클론 단계 이후로 토큰은 작업 공간에 남아 이후 모든 단계와 그 단계들이 실행하는 어떤 것에도 읽혔다. 서드파티 액션까지 포함해서다. 잡 어디서든 발생하는 코드 실행은 의도된 단계뿐 아니라 전부 탭 침해로 이어졌다.
- **문제 2 (`permissions: contents: write`가 필요 이상으로 넓음)**: 잡 자신의 읽기는 별도로 인증하는 `gh api`를 거친다. `GITHUB_TOKEN`의 `contents: write` 범위는 이 워크플로의 어느 단계도 쓰지 않았다.
- **문제 3 (동시성 제어 없음)**: 릴리스 두 개가 가깝게 게시되면 둘 다 같은 커밋에서 탭을 클론해 같은 파일을 다른 태그로 다시 쓴다. 두 번째 푸시는 non-fast-forward로 실패하고, 아무것도 하지 못한 채 먼저 푸시된 태그, 반드시 더 새 것은 아닌 태그만 조용히 남긴다.
- **문제 4 (에셋 목록을 페이지네이션 없이 읽음)**: 릴리스 객체에 임베디드된 `assets` 배열은 페이지네이션 제어도 문서화된 완전성 보장도 없다. 전용 `/releases/{id}/assets` 컬렉션과 다르다.
- **문제 5 (아티팩트를 탭 작업 트리 안에 내려받음)**: 내려받은 릴리스 아카이브 네 개를 커밋에서 빼는 유일한 안전장치가 커밋 단계에서 `Formula/all-smi.rb`를 명시적으로 지정하는 것뿐이었다. `git add -A` 한 번이면 바이너리를 Homebrew 탭에 그대로 게시하게 된다.
- **문제 6 (체크섬과 URL을 독립적으로 검증)**: "기대한 체크섬이 전부 존재한다"와 "기대한 URL이 전부 이 릴리스를 가리킨다"를 따로 검사하면, 값 하나하나는 개별적으로 통과하기 때문에 두 아티팩트의 체크섬이 뒤바뀐 폼을라도 받아들인다.
- **문제 7 (`packaging` 환경이 아무것도 게이트하지 않음)**: `protection_rules: []`와 `deployment_branch_policy: null`이므로, 환경 이름을 지정해도 비밀값을 그 잡에 한정할 뿐 누가 무엇으로 트리거할 수 있는지는 전혀 제한하지 않는다.

## 2. 기술적 검토 사항

### 2.1 보안: 이제 토큰이 어떻게 범위 지어지는가, 그리고 각 유출 경로가 왜 닫혔는가

`git push` 인증에 쓰이는 토큰이 샐 수 있는 경로는 뚜렷하게 네 가지이고, 이 PR은 넷 다 닫는다.

**디스크가 아니다.** 클론은 이제 익명이다(`git clone https://github.com/lablup/homebrew-tap.git`, 자격 증명 없음). 이게 가능한 이유는 `lablup/homebrew-tap`이 공개 저장소이고, 애초에 `brew tap lablup/tap`이 아무 자격 증명 없이 동작하려면 그래야 하기 때문이다. 토큰은 오직 푸시 단계에서만 등장하는데, 그 단계의 명령줄이나 환경 어디에도 원격 URL이나 설정 파일에 값을 쓰는 부분이 없다.

**argv가 아니다.** 자연스러운 대안인 `-c http.extraheader="Authorization: Basic $(printf ... | base64)"`는 인코딩된 토큰을 명령줄에 그대로 올려두므로, 프로세스가 살아있는 동안 `ps`로 읽히고 이후 단계가 `set -x`를 켜면 그대로 나타난다. 지금 선택된 형태는 값이 어떤 명령줄에도 문자 그대로 등장하지 않는다는 점에서 이를 피한다. 값은 셸 함수 안에서 환경 변수로부터 읽힐 뿐이다.

**`set -x` 추적도 아니다.** 이 부분이 미묘하고, 특정한 인용 방식이 필요한 이유이기도 하다.

```bash
# shellcheck disable=SC2016
git \
  -c credential.helper= \
  -c 'credential.helper=!f() { if [ "$1" = get ]; then printf "username=x-access-token\npassword=%s\n" "$HOMEBREW_TAP_TOKEN"; fi; }; f' \
  push origin main
```

헬퍼 문자열은 홑따옴표로 감싸져 있어서, `git push`를 호출하는 셸은 `$HOMEBREW_TAP_TOKEN`을 절대 확장하지 않는다. git은 실행할 헬퍼 프로그램으로 `$HOMEBREW_TAP_TOKEN`이라는 문자 그대로를 받는다. 이 줄을 `set -x`로 추적해도 트레이스에는 값이 아니라 확장되지 않은 그 이름이 그대로 나온다. 변수는 오직 git 자신이 헬퍼를 실행하려고 띄우는 일회용 셸(`sh -c 'f() { ... }; f'`) 안에서, 그 셸이 물려받은 환경으로부터만 풀린다. xtrace는 이 프로세스 경계를 넘지 못하는데, bash가 이런 방식으로 호출된 자식에 `SHELLOPTS`를 내보내지 않기 때문이다. 억제된 `SC2016` 린트가 바로 이 의도의 표식이다. 홑따옴표는 실수가 아니라 핵심이다.

**키체인도 아니다.** `-c credential.helper=`(빈 값)을 먼저 적용해 헬퍼 목록을 덧붙이는 대신 리셋한다. 그래서 러너 이미지가 전역으로 설정해둔 것(이 잡이 쓰는 `macos-latest` 러너에서는 `osxkeychain`)이 빠진다. 이 리셋이 없으면 인증 성공 후 그 사실이 이전에 설정된 헬퍼로 넘어가 저장되고, 이는 URL과는 다른 경로의 디스크 유출이 된다. 새 커스텀 헬퍼는 `get` 요청에만 응답한다. git의 인증 후 `store` 호출은 여전히 발생하지만, 헬퍼의 `if`가 이를 아무 일도 하지 않고 종료 코드 0을 내는 것으로 만들어서, git이 그 침묵을 헬퍼 실패로 오인해 재시도하거나 오류를 내지 않는다.

### 2.2 이슈 #316의 "에셋 28개" 전제가 틀린 지점

이슈 #316은 페이지네이션 수정의 근거로 "최근 릴리스가 이미 에셋 28개를 갖고 있어 곧 문제가 될 지경"이라고 적었다. 조사해보니 실제 개수는 28이 아니라 18이었고, 임베디드 `assets` 배열의 잘림은 전혀 재현되지 않았다. 이 워크플로가 읽는 것과 같은 엔드포인트로 `electron/electron`(에셋 76개)과 `denoland/deno`(56개) 모두 전체 목록을 인라인으로 돌려줬고, 이 프로젝트가 조만간 도달할 법한 어떤 개수에서도 상한의 흔적이 없었다.

그래도 수정은 유지했지만, 근거는 관측된 결함에서 문서화된 계약 논리로 바뀐다. 임베디드 `assets` 배열은 `Link` 헤더가 없고 GitHub는 그 완전성을 문서화해서 보장하지 않는 반면, `/releases/{id}/assets`는 문서화되어 명시적으로 페이지네이션되는 컬렉션이다. 이 워크플로는 인텔 에셋의 부재를 능동적 결정(스탠자 갱신 건너뛰기, 또는 다음 단계에서 버전 불일치 폼을라 거부)의 근거로 삼으므로, 그 결정을 문서화되지 않은 속성 위에 세우는 것 자체가 실제로 잘림이 있었는지와 무관하게 제거할 가치가 있다. 수정의 정당성이 애초 동기와는 다른 이유로 성립하는 사례라서 정확히 기록해 둘 만하다.

## 3. 기술적 선택과 그 이유

### 3.1 `http.extraheader` 대신 익명 클론과 명령 하나에 한정된 `credential.helper`

**컨텍스트**: 토큰은 잡 안에서 정확히 git 연산 하나(마지막 푸시)에만 닿아야 하고 그 밖 어디에도 닿아서는 안 된다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 토큰을 클론 URL에 두고 작업 공간이 임시라는 데 기댐 | 코드 변경 없음 | 정확히 지금 고치려는 결함이다. 토큰이 잡 전체 동안 모든 단계와 그 단계들이 실행하는 모든 것에 읽힘 |
| 푸시 시점에 `-c http.extraheader="Authorization: Basic $(...)"` | 흔한 패턴이고 원칙적으로는 명령 하나로 범위가 좁혀짐 | 인코딩된 토큰이 그 명령의 argv에 문자 그대로 등장해 `ps`와 단계 어디서든의 `set -x` 추적에 노출됨 |
| **채택: 익명 클론. 푸시 시점에 셸 함수 안에서 환경 변수로 토큰을 읽는 `credential.helper`** | 토큰이 클론 URL에도, argv에도, 추적에도 문자 그대로 등장하지 않음. 헬퍼 목록 리셋이 키체인 저장도 함께 막음 | 2.1절에 기록한 특정한 홑따옴표 규율이 필요함. 부주의한 편집(헬퍼 문자열을 겹따옴표로 바꾸는 것)이 조용히 argv·추적 유출을 되살릴 수 있음 |

**선택 이유**: 익명 클론은 탭이 공개 저장소이기 때문에만 가능한데, 어차피 평범한 `brew tap` 사용을 위해서도 공개여야 하므로 클론 자격 증명을 완전히 없애도 잃는 능력이 없다. 남은 자격 증명을 명령의 인자가 아니라 명령의 환경으로 범위 짓는 것이, `ps` 가시성과 `set -x` 추적 둘 다를 한 번에 무력화하는 지점이다. 둘 다 명령줄을 공격 대상으로 삼지 프로세스 환경을 대상으로 삼지 않기 때문이다.

### 3.2 url과 체크섬을 독립 집합이 아니라 쌍으로 검증

**컨텍스트**: 이전 검증은 "기대한 sha256 값이 파일 어딘가에 전부 나타난다"와, 따로 "기대한 URL이 파일 어딘가에 전부 나타난다"를 확인했다. 두 아티팩트의 체크섬이 뒤바뀐 폼을라는 두 검사를 개별적으로는 통과한다.

**채택한 수정**: `set_artifact`가 폼을라를 쓰는 것과 같은 방식으로 쌍을 뽑는다. `url` 스탠자 다음에 바로 아래 있는 `sha256` 스탠자를 짝짓는다. 그리고 기대하는 `(url, sha256)` 쌍 각각을 그 추출된 목록에 대고 하나의 단위로 확인한다.

```bash
awk '
  /^[[:space:]]*url "/ { u = $0; sub(...); pending = 1; next }
  pending && /^[[:space:]]*sha256 "/ { s = $0; sub(...); printf "%s\t%s\n", u, s; pending = 0 }
' Formula/all-smi.rb > "$pairs"
```

**선택 이유**: 체크섬이 뒤바뀌는 것은 가상의 실패 양상이 아니다. 한 스탠자를 매칭해 다른 스탠자에 쓰는 재작성 결함이 정확히 만들어낼 결과이며, 이는 전체 갱신 단계가 애초에 막으려는 바로 그 부류의 버그다. 테스트 스위트의 대조 하나가, #318 이전의 독립 검사가 체크섬을 고의로 뒤바꾼 픽스처를 받아들인다는 것을 확인해 준다. 이것이 쌍을 검증 단위로 삼도록 만든 근거다.

### 3.3 `packaging` 환경을 설정하는 대신 그 결정을 기록

**컨텍스트**: 잡에 GitHub Environment 이름을 지정하면 그 잡의 접근을 환경의 비밀값으로 한정하지만, 환경 자체에 보호 규칙(필수 리뷰어, 배포 브랜치 정책)이 있을 때만 접근을 게이트한다. `packaging`에는 둘 다 없다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 이 PR에서 필수 리뷰어나 브랜치 정책을 추가 | 공백을 완전히 닫음 | 누가 릴리스를 낼 수 있는지를 결정하는 저장소 관리 변경이다. 워크플로 강화 PR에 조용히 끼워 넣을 일이 아님 |
| **채택: 설정하지 않겠다는 결정을, 잡에 대한 주석과 이 PR의 설명 양쪽에 기록** | 결정과 그 이유를 제자리인 유지관리자에게 남김. 이슈가 명시적으로 허용하는 수용 기준("설정하거나, 하지 않겠다는 명시적 결정을 기록하거나")을 충족함 | 공백은 유지관리자가 행동할 때까지 열려 있음 |

**선택 이유**: 프로덕션 Homebrew 탭에 푸시할 수 있는 워크플로를 누가 트리거할 권한을 갖는지는 구현 문제가 아니라 정책 문제다. 결국 스크롤되어 사라질 PR 설명뿐 아니라 워크플로 파일 안, `environment: packaging` 바로 옆에 그 이유를 남겨두면 이 파일을 다음에 읽는 사람에게도 열린 결정이 계속 보인다.

## 5. 학습 포인트

### 5.1 클론 URL에 박힌 자격 증명은 클론 명령이 아니라 작업 트리 전체 수명 동안 남는다

**개념**: `git clone https://user:token@host/repo.git`이 편리한 이유는 git이 이를 기억한다는 데 있다. URL을 `origin` 원격으로 `.git/config`에 그대로 적어둔다. 오래 유지되는 클론에서는 이 지속성이 기능이지만, 이후 단계와 그 단계들이 실행하는 모든 것이 그 파일을 읽을 수 있는 CI 잡에서는 취약점이 된다.

**이 PR에서의 적용**: 익명 클론과 푸시 시점 전용 자격 증명이, 범위를 좁힌 클론 자격 증명으로는 닫을 수 없는 이 공백을 정확히 닫는 이유가 여기 있다. 자격 증명이 필요한 명령 하나를 넘어서는 것과는 아예 접촉하지 않기 때문이다.

### 5.2 `set -x` 추적은 셸이 겹따옴표를 확장한 결과가 아니라 작성된 그대로의 명령을 찍는다

**개념**: bash의 xtrace는 단어 분리와 확장을 거친 뒤(띄운 셸의 경우 그 셸 자신의 확장 이전에) 각 명령을 찍는다. 확장되지 않은 `$VAR` 참조를 담은 홑따옴표 문자열이라면, 트레이스에 나타나는 것도 정확히 그 문자 그대로다. 바깥 셸이 이를 확장한 적이 없기 때문이다.

**이 PR에서의 적용**: 자격 증명 헬퍼 문자열이 홑따옴표로 감싸진 이유는, `$HOMEBREW_TAP_TOKEN`이 오직 git이 헬퍼 실행을 위해 띄우는 일회용 셸 안에서만 풀리고, `git push` 줄 자체를 실행하는 셸에서는 절대 풀리지 않게 하기 위해서다. 그 줄을 추적해도 확장되지 않은 변수 이름만 보이고, 실제 값은 어떤 로그에도 등장하지 않는다.

### 5.3 독립적으로 옳은 검사 두 개가 짝을 이룬 검사와 같은 보증은 아니다

**개념**: "기대값 A가 어딘가에 전부 있다"와 "기대값 B가 어딘가에 전부 있다"를 따로 확인해도 "모든 A가 자신의 올바른 B와 짝지어져 있다"는 결론은 나오지 않는다. 두 아티팩트의 체크섬을 뒤바꾼 폼을라는 두 독립 검사를 통과하면서도 `brew install`이 실제로 의존하는 불변식은 어긴다.

**이 PR에서의 적용**: `(url, sha256)`를 인접한 쌍으로 추출해 그 쌍을 하나의 단위로 확인하는 것이 이 공백을 닫는다. PR의 테스트 스위트는 새 짝짓기 검사가 이를 거부한다는 것을 확인하기 전에, 먼저 그 실패 양상이 실제로 존재함을(체크섬을 뒤바꾼 픽스처가 옛 독립 검사를 통과함을) 확인한다.

## 6. 추가 학습

### 핵심 용어

| 용어 | 설명 | 관련성 |
|---|---|---|
| `credential.helper` | 원격 연산에 대한 인증을 공급하고 선택적으로 저장하는 git의 확장 가능한 메커니즘 | 이 PR이 탭 토큰을 명령 하나에 한정하는 데 쓰는 메커니즘 |
| `http.extraheader` | `Authorization` 헤더를 직접 공급하는 또 다른 git 설정 | 인코딩된 토큰이 명령줄에 문자 그대로 등장하기 때문에 배제됨(3.1절) |
| GitHub Actions `set -x` / xtrace | CI 디버깅을 위해 흔히 켜는 bash 명령 에코 추적 | 어설프게 인용된 자격 증명 헬퍼가 빠질 유출 경로(2.1, 5.2절) |
| `/releases/{id}/assets` 대 임베디드 `assets[]` | GitHub API로 릴리스 에셋 목록을 읽는 두 방법. 하나는 페이지네이션되고 문서화되어 있고, 하나는 임베디드되어 있고 문서화되어 있지 않음 | 2.2절의 "근거는 달랐지만 수정은 옳았다" 발견 |
| `concurrency:` 그룹 | 같은 그룹 이름을 공유하는 워크플로 실행을 순서대로 처리하는 GitHub Actions 기본 요소 | 릴리스 두 개가 같은 탭 푸시에서 경합하는 것을 막음 |
| GitHub Environment 보호 규칙 | 이름 있는 환경에 붙는 필수 리뷰어·배포 브랜치 정책 | `packaging`에 여전히 없는 것. 유지관리자의 결정으로 기록됨(3.3절) |

### 관련 기술/프레임워크

- Git 자격 증명 헬퍼와, 설정 하나를 단일 호출에 한정하는 `-c` 오버라이드 메커니즘.
- GitHub Actions `concurrency:` 그룹과 `permissions:` 범위 지정.
- GitHub REST API 페이지네이션(`Link` 헤더, `--paginate`)과 임베디드되어 문서화되지 않은 배열 필드의 대비.

## 8. 후속 조치

### 필수

- **실제 태그에 대한 드라이런.** 의도적으로 시도하지 않았다. 프로덕션 탭 `lablup/homebrew-tap`을 상대로 릴리스를 게시하거나 워크플로를 디스패치해야 하는데, 이는 강화 PR의 일부로 할 일이 아니다. 대신 푸시 메커니즘은 인증 기능을 갖춘 로컬 git smart-HTTP 서버(`git-http-server.py`)로 검증했다. 이는 자격 증명 범위 지정 로직은 증명하지만, GitHub가 실제 저장소에 대해 실제 토큰을 받아들이는지는 증명하지 못한다.

### 유지관리자에게 남겨둠

- **`packaging` 환경에 보호 규칙이 없는 것.** 의도적인 결정으로 기록했고(3.3절) 여기서 고치지 않았다. 필수 리뷰어나 배포 브랜치 정책을 추가할지는 유지관리자가 결정해야 한다.
- **부하 상황에서의 실제 GitHub API 페이지네이션.** `--paginate` 동작은 테스트 하네스의 스텁에 대고 확인했다. 실제 호출로 현재 릴리스에서 임베디드 배열과 같은 에셋 이름 18개를 돌려줌을 확인했지만, 진짜 두 번째 페이지를 강제할 만큼 에셋이 많은 릴리스는 아직 없다.
- **실제 겹치는 릴리스에서의 `concurrency`.** 그룹은 선언되어 있고 형태가 파싱됨을 확인했지만, 실제로 동시에 게시되는 릴리스 두 개를 실제 워크플로에 대고 시도한 적은 없다.

### 결함 아님, 의도된 동작

- 이슈 #316의 "에셋 28개" 전제는 성립하지 않는다(실제 개수는 18개이고 잘림은 재현되지 않았다). 페이지네이션 수정은 관측된 잘림이 아니라 2.2절의 문서화된 계약 논리 위에서 유지됐다.
