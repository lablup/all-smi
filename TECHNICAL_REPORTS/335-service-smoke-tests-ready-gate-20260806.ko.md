## 요약

`systemd-service` 잡은 `systemctl is-active`를 기다린 다음 `curl -sf .../metrics | head -5`를 단언했는데, 이 단언은 절대 실패할 수 없다. `head`가 파이프라인의 종료 코드를 삼켜버리기 때문이다. 이건 올바른 게이트가 아니라 PR #323이 launchd 쪽에서 고쳤던 것과 같은 게이트-단언 불일치를 가리고 있는, 더 약한 단언일 뿐이다. 단언만 강화했다면 PR #323이 고쳤던 바로 그 경합(31005178260번 실행이 243밀리초 차이로 진 그 경합)을 다시 불러왔을 것이다. PR #335는 두 잡의 준비 상태 게이트를 전부 `/-/ready` 폴링으로 바꾼다. 이 엔드포인트는 두 커밋 전에 PR #333이 추가한 것이다. 근거는 게이트가 반드시 다운스트림 단언이 의존하는 것과 *같은 이벤트*를 확인해야지, 우연히 비슷한 시점에 참이 되는 조건이면 안 된다는 것이다. `/-/ready`의 200 전환과 `all_smi_memory_total_bytes`의 노출은 `collection_loop.rs` 안에서 일어나는 같은 `AppState` 쓰기지, 그저 상관관계가 있는 두 관측치가 아니다.

더 날카로운 발견은 같은 병합 시퀀스 안에서 두 커밋 전 PR #333이 PR #323 자신의 게이트에 한 일이다. PR #323은 launchd 잡을 콘텐츠 폴링(`grep -q '^all_smi_'`)으로 단단히 고쳤는데, 그 근거는 빈 `AppState`가 바이트 길이 0인 본문을 렌더링한다는 것이었다. PR #333은 `all_smi_up`/`all_smi_build_info` 기준선을 무조건적으로 만들었고, 이는 실제 수집이 일어나기도 전인 첫 요청부터 `^all_smi_`가 매치된다는 뜻이다. 그러니 PR #323 자신의 주석 블록은 거짓이 됐고, 그 게이트는 #323 이전 게이트가 그랬던 것과 똑같이 즉시 열려서 다시 경합했을 것이다. launchd 잡을 `/-/ready`로 옮긴 건 이슈 #329가 복수형으로 적어둔 "이 CI 게이트들이 이를 받아들여야 한다"에 맞춰 굳이 범위를 챙기는 선택 사항이 아니었다. 손대지 않고 두었다면 깨진 게이트가 launchd 잡 코드 자체는 건드린 적도 없는 PR에 의해 조용히 다시 심어졌을 것이다. systemd 잡의 준비 상태 게이트, 크래시 복구 후 점검, 재시작 후 점검이 전부 `http://127.0.0.1:19191/-/ready`를 폴링하는 같은 `ready()` 헬퍼로 옮겨간다. launchd 단언은 콘텐츠 기반을 유지하되 `all_smi_up`/`all_smi_build_info` 기준선에 대한 명시적 점검이 추가된다. 전체 규모는 파일 1개, +112/-26, 커밋 1개, #329를 닫는다.

## 1. 문제 정의

### 1.1 배경

PR #323(보고서: `323-launchd-smoke-test-race-20260805`)은 launchd 스모크 테스트에서 게이트-단언 불일치를 진단하고 고쳤다. 준비 상태 대기가 다음에 오는 단언(지표 콘텐츠 존재)보다 더 약한 조건(HTTP 200)을 확인했고, 둘 사이 간격이 launchd의 `ProcessType=Background` 스케줄링 아래서는 CI에서 경합에 질 만큼 넓었다. 이슈 #329는 `systemd-service` 잡의 시스템 스코프 스텝이 똑같은 모양(게이트는 `systemctl is-active`, 단언은 `curl -sf | head -5`)을 갖고 있다는 걸 발견하고 같은 방식으로 고쳐야 하는지 물었는데, 이슈 #324(PR #333이 구현하는 준비 상태 계약)가 답을 바꿀 수 있다는 점도 함께 짚었다.

### 1.2 기존 문제점

- **문제 1 (systemd 게이트가 단언보다 더 약한 조건을 확인함)**: `Type=exec` 아래에서 `systemctl is-active`는 유닛의 바이너리가 실행되는 즉시 active를 보고한다. 리스너가 바인딩됐는지, 수집 주기가 돌았는지와는 무관하다.
- **문제 2 (systemd 단언이 잡아야 할 불일치에서 실패할 수 없음)**: `curl -sf .../metrics | head -5`는 빈 본문에서 실패할 수 없다. `head`가 파이프라인의 종료 코드를 삼키기 때문이다. 이 잡이 PR #323의 잡이 진 경합을 지지 않은 이유는 게이트가 옳아서가 아니라 단언이 약해서일 뿐이었다.
- **문제 3 (`curl -sf .../metrics`는 이제 영구히 준비 상태 게이트로 쓸 수 없음)**: PR #333이 `/metrics`를 리스너가 바인딩되는 순간부터 200을 답하게 의도적으로 만들었으므로, 평범한 200 게이트는 다시는 "떴음"과 "떴고 준비됐음"을 구분할 수 없다.
- **문제 4 (PR #323 자신의 콘텐츠 게이트가 조용히 깨짐)**: PR #333의 무조건 기준선 때문에 `grep -q '^all_smi_'`가 수집 루프가 아무것도 쓰기 전인 첫 요청부터 매치된다. 그러니 실제 조건을 확인하도록 옮기지 않는 한 launchd 잡의 게이트는 즉시 열려서 PR #323이 고친 바로 그 243밀리초짜리 경합을 다시 불러온다.
- **문제 5 (병합 시점에 systemd 잡의 바뀐 코드가 실행되지 않음)**: 이 PR이 다시 쓰는 준비 상태 게이트가 들어있는 시스템 스코프 스텝은 여전히 `steps.probe.outputs.user_scope != 'true'`라는, `ubuntu-latest`에서는 절대 성립하지 않는 조건 뒤에 있었다. 그래서 이 PR의 systemd 쪽 변경은 자기 자신의 CI 실행에서도 검증되지 않았다. 실제로 돈 건 launchd 잡의 이관된 게이트뿐이다.

### 1.3 위험성

| 위험 | 영향 | 발생 가능성 |
|---|---|---|
| PR #333 이후에도 launchd 잡의 콘텐츠 게이트를 옮기지 않고 둠 | High: 게이트가 첫 요청부터 열려서, launchd 잡 자체는 아무것도 바뀌지 않았는데도 PR #323이 고쳤던 바로 그 경합이 눈에 띄는 방아쇠 없이 다시 심어짐 | PR #333 병합 뒤 다음 launchd 잡 실행에서 발생했을 것. 이 PR이 그 직후에 병합되어 회피됨 |
| 게이트는 고치지 않고 systemd 단언만 강화 | High: PR #323이 고친 것과 같은 유형의 플레이크가 이번엔 systemd 잡에서 재발 | 이 PR이 게이트와 단언을 함께 고쳐서 회피 |
| CI에서 실행되지 않는 코드 경로를 기준으로 systemd 게이트 변경을 검증했다고 주장함 | Medium: "잡이 main에서 통과한다"는 PR 자신의 인수 기준을 실행되지 않은 경로의 근거로 주장할 수 있었음 | 명시적으로 그렇게 주장하지 않음. PR은 유저 스코프 경로에 대해서만 기준을 체크했고, 시스템 스코프 검증은 PR #330으로 미룸 |

## 2. 기술적 검토 사항

### 2.1 정확성

핵심 설계 선택은 단언이 의존하는 것과 상관관계 있는 대체물이 아니라 같은 *이벤트*로 게이트를 거는 것이다. `collection_loop.rs`는 `guard.memory_info`를 대입하는 것과 같은 쓰기 락 블록 안에서 `loading`을 해제한다. 그러니 `/-/ready`가 200을 반환하는 것과 `all_smi_memory_total_bytes`가 렌더링 가능해지는 것은 시간상 우연히 겹치는 두 사건이 아니라, 서로 다른 엔드포인트 두 개에서 관측한 같은 쓰기다. 이건 PR #323의 콘텐츠 게이트가 제공했던 것보다 강한 관계다. 그 게이트는 지표 줄의 존재를 폴링했는데, 이게 준비 상태 조건과 같은 순간 참이 됐던 건 게이트가 준비 상태를 직접 확인해서가 아니라 둘 다 같은 수집 주기의 하류였기 때문일 뿐이다. systemd 잡에서 9090이 아니라 19191 포트로 `/-/ready`를 폴링하는 것도 편의가 아니라 정확성을 위한 장치다. #309/#330의 `/etc/all-smi/config.toml` 탐색이 제대로 동작한다면 대상 포트와 설정으로 지정한 포트는 같은 값이어야 하니, 19191에 대한 성공적인 폴링 자체가 설정 파일이 리스너를 옮겼다는 부분적인 증거가 된다.

### 2.2 성능 관점

측정 가능한 변화는 없다. 게이트 루프는 구조상 PR #323의 것과 동일하고(`for _ in $(seq 1 60); do ...; sleep 2; done`), 그냥 다른 엔드포인트를 가리킬 뿐이다. 총 대기 시간은 같은 방식으로 상한이 걸려 있고, 잡의 전체 시간 비용은 cargo 빌드가 지배하기 때문에 이 PR과 무관하다.

### 2.3 호환성 및 의존성

- **Breaking Changes**: 없다. 이 PR은 `.github/workflows/ci.yml`만 건드린다.
- **새로운 의존성**: 없다. 이미 병합된, PR #333이 추가한 `/-/ready` 라우트에 의존할 뿐이다.
- **호환성**: Rust 소스는 하나도 바뀌지 않았으므로 이 diff에는 `cargo` 검사가 해당되지 않는다. PR 자신의 테스트 계획도 이를 반영한다.

### 2.4 코드 품질

`ready()` 헬퍼는 systemd 잡과 launchd 잡에 각기 조금씩 다르게(포트가 다르고 진단 덤프가 다름) 중복되어 있다. 공유 스크립트나 컴포지트 액션을 새로 만드는 대신 PR #323이 세운 모양을 그대로 따른 것이다. 덕분에 diff가 작게 유지되고 각 잡의 실패 진단이 자기완결적이다(타임아웃 시 둘 다 마지막 `/-/ready` 응답과 마지막 `/metrics` 응답을 덤프하고, systemd 쪽은 `ss -lntp`도 추가로 덤프한다). systemd 잡의 크래시 복구와 `restart` 점검에는 이전에 사후 준비 상태 단언이 전혀 없었다. 이 PR이 둘 다 뒤에 `ready` 호출을 추가해서, `restart` 자신의 종료 코드만이 교체된 프로세스가 실제로 떴는지 알려주는 유일한 신호였던 상황을 벗어난다.

## 3. 기술적 선택과 그 이유

### 3.1 진짜 준비 상태 엔드포인트가 생긴 이상, 더 강한 콘텐츠 검사가 아니라 `/-/ready`로 게이트를 건다

**컨텍스트**: 이슈 #324/PR #333이 병합된 상태에서 systemd 잡의 게이트를 고칠 방법은 여러 가지였다. `curl -sf | head -5`를 콘텐츠 검사(`grep -q '^all_smi_'`, 이 PR 이전 PR #323의 launchd 수정을 그대로 따라 함)로 강화하거나, 새 `/-/ready` 엔드포인트를 채택하는 것이다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| PR #323 그대로 따라가기: `grep -q '^all_smi_'`로 게이트 | launchd에서 이미 입증된 패턴과 일관성 유지 | 이 PR이 채 반영하기도 전에 PR #333의 무조건 기준선 때문에 이미 깨져 있음. 즉시 두 번째 수정이 필요해짐 |
| **채택: `/-/ready`로 게이트** | 단언이 의존하는 정확한 이벤트(같은 `AppState` 쓰기)를 확인함. 콘텐츠 패턴 게이트와 달리 미래에 무조건 지표군이 하나 더 생겨도 영향받지 않음 | 엔드포인트가 존재해야 하는데, PR #333으로 이미 존재함 |
| `systemctl is-active`/`curl -sf`를 유지하고 위험을 감수 | 변경이 필요 없음 | PR #323이 고쳤던 바로 그 불일치가 systemd 잡에 그대로 남음. 곧바로 기각 |

**선택 이유**: 특정 렌더링된 지표 이름에 걸린 게이트는 익스포터 변경 한 번이면 다시 깨질 수 있다는 걸 PR #333이 PR #323 자신의 게이트에 대해 정확히 보여줬다. `/-/ready`는 게이트가 답을 얻어야 할 바로 그 질문에 답하도록 목적에 맞게 만들어졌고, 노출 로직의 `all_smi_up` 게이지가 쓰는 것과 같은 술어로 정의된다. 그래서 `grep` 패턴과 달리 무관한 지표 변경으로 무효화될 수 없다.

### 3.2 launchd 잡의 게이트도 함께 옮긴다. 이슈 #329의 범위를 명시적으로 이를 포함하는 것으로 취급하지, 범위 밖의 배려로 취급하지 않는다

**컨텍스트**: 이 PR을 이끈 브리프는 launchd 잡을 옮기는 걸 일관성과 범위 규율 사이의 판단 문제로 프레이밍했다. 이슈 #329의 제목과 근거 섹션이 구체적으로 systemd 잡을 겨냥하고 있었기 때문이다.

**결정**: 옮긴다. 이슈 #329의 범위(Scope) 섹션 자체가 복수형으로 "#324가 진짜 준비 상태 계약을 들여오면 이 CI 게이트들은 콘텐츠 폴링을 유지하는 대신 이를 받아들여야 한다"("게이트들"이지 "게이트"가 아님)고 적어놓았고, 이는 두 잡 모두를 건드리는 걸 사전에 승인한다. 문자상의 승인을 넘어서, 두 가지 사실이 손대지 않고 두는 쪽을 보수적인 선택이 아니라 더 나쁜 선택으로 만든다. PR #323의 주석 블록은 빈 `AppState`가 바이트 길이 0인 본문을 렌더링한다는 주장에 구체적으로 근거해 콘텐츠 게이팅을 정당화했는데, PR #333이 이 주장을 거짓으로 만들었다. 그리고 같은 PR #333 변경 때문에 PR #323의 `grep -q '^all_smi_'` 패턴은 이제 첫 요청부터 매치된다. 그러니 옮기지 않으면 게이트는 즉시 열려서 다시 경합한다.

**선택 이유**: 이건 범위 확장이 아니라 같은 병합 시퀀스가 두 커밋 전에 만들어낸 결함을 닫는 것이다. PR #333 병합 후에도 PR #323 형태 그대로 남은 게이트는, launchd 잡의 그 파일 부분을 건드린 적도 없는 PR에 의해 조용히 깨졌을 것이다.

### 3.3 launchd 단언은 `/-/ready`로 옮기지 않고 콘텐츠 기반으로 유지한다

**컨텍스트**: 게이트가 `/-/ready`를 쓰게 된 이상, 다운스트림 단언도 원칙적으로는 특정 지표 콘텐츠를 확인하는 대신 그냥 `/-/ready` 상태를 다시 확인하면 될 수도 있었다.

**결정**: (launchd에는 `^all_smi_up`, `^all_smi_build_info`, `^all_smi_memory_total_bytes`, systemd에는 `^all_smi_memory_total_bytes`) 콘텐츠 단언을 `/-/ready` 게이트 대신이 아니라 그 위에 계속 유지한다.

**선택 이유**: `/-/ready`는 수집 주기가 끝났다는 걸 증명할 뿐, 이 특정 러너에서 노출 로직이 실제로 어떤 지표군을 렌더링했는지는 그 자체로 증명하지 못한다. launchd 잡은 IOReport가 없는 macOS VM에서 도는데, 콘텐츠 단언은 macOS 전용 저하 경로(네이티브 GPU/섀시 지표는 없고 메모리 지표는 있음)가 여전히 실제 데이터를 만들어낸다는 걸 증명하기 위해 존재한다. 이건 "서비스가 준비됐다"보다 더 구체적이고 다른 주장이다. 둘을 하나의 검사로 합치면 그 구체성을 잃는다.

**파일: `.github/workflows/ci.yml`(systemd 잡의 새 게이트)**

ready() {

      return 0
    fi
    sleep 2
  done

# Assert on rendered content, not on the port merely answering.
# `all_smi_memory_total_bytes` rather than a bare `^all_smi_` prefix:

## 5. 학습 포인트

### 5.1 렌더링된 콘텐츠 위에 세운 게이트는 노출 로직 자신의 "항상 존재하는" 집합만큼만 안정적이다

**개념**: 특정 패턴에 매치되는 줄을 폴링하는 CI 게이트는 암묵적으로 그 패턴의 의미가 고정돼 있다는 데 걸고 있는 것이다. 나중의 변경이 그 패턴을 무조건 매치되게 만들면(의도적으로 추가된 항상-존재 기준선처럼), 게이트 자신의 코드는 하나도 안 바뀌었는데도 조용히 아무 의미 있는 것도 게이팅하지 않게 된다.

**이 PR에서의 적용**: PR #323의 `grep -q '^all_smi_'` 게이트는 작성 당시엔 옳았다. 전혀 다른 서브시스템을 다룬 무관한 PR인 PR #333이 두 커밋 뒤에 설계상 이를 무효화했다. `/-/ready`가 정확히 면역인 실패 모드가 바로 이것이다. 노출 콘텐츠에 대한 패턴이 아니라 전용 술어를 근거로 삼기 때문이다.

### 5.2 "아직 실패한 적 없다"는 게이트가 옳다는 증거가 아니다. 업스트림 변경 직후라면 더더욱 그렇다

**개념**: 계속 green이었던 CI 잡이라고 해서 게이트가 올바른 조건을 확인한다는 증거는 아니다. 그저 아직 새로운 실패 모드에 노출된 적이 없을 뿐일 수도 있다. systemd 잡의 `curl -sf | head -5`가 한 번도 실패하지 않았던 건 옳은 게이트여서가 아니라, `head`가 구조적으로 잡아야 할 실패를 관측할 수 없었기 때문이다.

**이 PR에서의 적용**: 이 PR은 systemd 잡이 실제로 플레이크를 내는 걸 기다리지 않고 고친다. launchd 쪽에서 실제 실패가 나온 뒤 대응했던 PR #323과는 다른 자세다. 여기서는 이슈 #329가 지목한 것과 똑같은 모양의 불일치를 실제로 나타나기 전에 알아채서 선제적으로 고쳤다.

### 5.3 업스트림 계약에 기대는 수정이라면, 그 계약을 건드리는 커밋마다 가정을 다시 검증한다

**개념**: 다른 서브시스템의 동작(여기서는 어떤 지표 줄이 항상 존재하는가)에 의존하는 CI 게이트는 그 서브시스템이 바뀔 때마다 다시 검사해야지, 한 번 짜놓고 신뢰만 해서는 안 된다.

**이 PR에서의 적용**: 이 PR은 PR #333의 기준선 변경이 PR #323의 게이트에 미치는 영향을 명시적으로 추적하지, 두 PR을 무관한 것으로 취급하지 않는다. 이 추적이 바로 이 보고서가 첫머리에 내세운 "가장 날카로운 발견"을 드러낸 지점이다.
