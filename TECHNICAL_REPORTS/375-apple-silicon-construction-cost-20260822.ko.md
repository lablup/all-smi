# 기술 보고서: PR #375 - Apple Silicon 클라이언트 생성 비용을 1.4초에서 0.28초로 단축

**일자**: 2026-08-22  
**상태**: 완료  
**관련 항목**: PR #375, 이슈 #374  
**위험 수준**: 중간 (프로세스 전역 매니저 수명과 SMC 키 탐색 방식을 변경)

---

## 요약

`AllSmi::with_config`는 Apple Silicon에서 반환 전에 1초 넘게 블록됐고, 그 전부가 `get_gpu_readers` → `NativeMetricsManager::new`에 있었습니다. 이슈 #374는 독립적인 원인 셋을 지목하며, 각각을 여기서 개별적으로 고쳤습니다.

Apple M5 Max(Mac17,7, macOS 26.6.2 25G83)에서 첫 생성이 **1.28~1.54초에서 273~285밀리초로**, 이후 생성이 **275~281밀리초에서 131~136밀리초로** 떨어졌습니다. 작업 중 발견한 네 번째 결함(한 클라이언트를 드롭하면 다른 클라이언트가 무력화되는 문제)도 같은 PR에서 고쳤습니다.

---

## 1. 문제 정의

생성자 하나에 비용 셋이 쌓여 있었습니다.

- `discover_temperature_keys`가 M5 Max SMC 표의 키 3,739개 전부를 키당 IOKit 왕복 두 번씩 스캔했습니다. early exit 조건이 CPU와 GPU 범주 **양쪽**이 공유 64키 상한을 채울 것을 요구했는데, 실제 Mac 중 양쪽을 채우는 기종이 없기 때문입니다. 측정값은 CPU 키 23개, GPU 키 84개, 상한 64였습니다.
- `IOReport::new`가 생성마다 `IOReportCopyChannelsInGroup` 호출 세 개를 연달아 발행하고 병합했습니다.
- 공유 64키 상한이 GPU 센서 집합을 잘라내, 보고 온도가 키 표에 우연히 먼저 나열된 64개 센서의 평균이 됐습니다.

## 3. 기술적 선택과 그 이유

### 3.1 SMC 키 탐색이 표 전체 순회 대신 구간을 이진 탐색

키 표는 FourCC 순으로 정렬돼 있고 모든 후보 이름이 `T`로 시작하므로, 후보 전체가 연속된 구간 하나를 차지합니다. 이제 탐색은 그 구간의 시작을 이진 탐색으로 찾고 끝까지만 순회하며, 분류될 가능성이 없는 이름에 대해서는 두 번째 왕복(`read_key_info`)을 건너뜁니다.

**3,739개 대신 373개 인덱스를 읽고**, **1.05초가 80밀리초가 됩니다.**

### 3.2 정렬 여부를 가정하지 않고 검사한다

표 전체를 읽지 않고서는 정렬돼 있음을 증명할 수 없으므로, 빠른 경로는 가용한 값싼 검사 두 가지를 취하고 뒤를 받칩니다.

- 이진 탐색이 이미 읽은 인덱스들이 비감소여야 하고,
- 구간 바로 아래 키가 구간보다 앞서 정렬돼야 하며,
- 센서를 하나도 내놓지 못한 구간은 센서 없는 머신이 아니라 실패한 가정으로 취급합니다.

이 중 하나라도 걸리면 전수 스캔을 돌립니다. 전수 스캔은 표에 무엇이 있는지에 대한 권위로 남으며, 이름 사전 필터 덕분에 이전보다 자체적으로도 저렴합니다. `the_span_search_finds_what_the_full_scan_finds`가 실하드웨어에서 두 경로가 동일한 키를 반환함을 단언합니다.

### 3.3 채널 열거를 동시 실행하고 프로세스당 한 번만

`IOReportCopyChannelsInGroup` 호출 세 개는 나중에야 결합되는 독립적인 읽기이므로 이제 동시에 실행되며(측정값 137밀리초 → 62밀리초), 머신이 노출하는 채널 집합은 하드웨어로 고정되므로 병합된 딕셔너리를 프로세스 전역으로 캐시합니다. 각 구독은 자기 `CFDictionaryCreateMutableCopy`를 가져가므로 캐시된 기술자는 원본 그대로 유지됩니다.

기존 비대칭은 의도적으로 보존했습니다. Energy Model 그룹은 계속 치명적이고, CPU/GPU stats는 계속 부재를 허용합니다. 뭉개는 대신 구분을 두 가지 추가했습니다.

- 패닉한 열거 스레드를 호스트에 애초에 없는 그룹과 구분해 보고합니다.
- 자원 압박으로 OS가 스레드 생성을 거부하면, `AllSmi::with_config` 밖으로 패닉하는 대신 그 질의를 인라인으로 실행합니다. 이 함수의 계약은 실패를 `Result`로 보고하는 것입니다.

### 3.4 한 클라이언트 드롭이 다른 클라이언트를 무력화하지 않는다

`AllSmi::drop`이 `shutdown_native_metrics_manager`를 호출했고, 이 함수는 다른 누가 붙들고 있든 상관없이 프로세스 전역 매니저를 슬롯에서 꺼냈습니다. 아직 자기 리더를 건드리지 않은 두 번째 클라이언트는 매니저를 찾지 못해 살아 있는 GPU 필드를 전부 사용 불가로 보고했습니다. 수정 전 재현:

```
a:                                    util=Some(0.61)  power=Some(0.0085)
b (a 드롭 후 최초 사용):              util=Some(-1.0)  power=Some(-1.0)   <- GPU_METRIC_UNAVAILABLE
```

이제 매니저가 소유 핸들을 셉니다. `AllSmi`가 하나를 획득하고 드롭 시 반납하며, 마지막 하나가 사라질 때 해체가 일어납니다. `shutdown_native_metrics_manager`는 바이너리를 위한 무조건 프로세스 종료 의미론을 유지하며, 바이너리는 이 계수에 참여하지 않습니다. 부수 수정으로 수집기 스레드 join을 싱글턴 락 아래가 아니라 바깥에서 수행하도록 옮겼습니다.

### 3.5 GPU 키 상한을 범주별로 나누고 절삭을 없앤다

M5 Max는 `Tp*`/`Te*` 23개 대비 `Tg*` 센서 84개를 노출하므로, 기존 공유 상한 64가 GPU 집합을 잘랐습니다. 이제 두 상한 모두 실하드웨어보다 크게 잡아 폭주 가드 역할만 하며, 이로써 보고 온도가 키 정렬 순서가 아니라 센서의 함수가 됩니다.

**이는 이슈가 제안한 더 작은 `Tg*` 상한과 반대 방향**이며, 그 근거를 기록해 둘 가치가 있습니다. 이슈가 밝힌 우려는 값이 "열거된 것들에 희석된다"는 것인데, 그것을 일으키는 원인이 임의의 앞 N개 부분집합입니다. 절삭을 없애는 것이 그 우려를 직접 다루고, 상한을 낮추면 값이 계속 순서 의존으로 남습니다. 64개 대신 84개 센서를 모두 덮는 측정 비용은 읽기당 약 0.3밀리초입니다.

## 4. 측정

릴리스 빌드, `default-features = false`, Apple M5 Max. `origin/main`과 이 브랜치를 별도 워크트리에 빌드해 **같은 세션에서 교대로** 세 라운드 실행했으므로 열 드리프트가 양쪽에 동등하게 작용합니다.

| | 이전 (`origin/main`) | 이후 |
|---|---|---|
| 첫 `AllSmi::with_config` | 1.280s / 1.518s / 1.536s | 273ms / 275ms / 285ms |
| 이후 `with_config` | 275~281ms | 131~136ms |
| `discover_temperature_keys` | 933ms / 953ms / 1.271s | 77ms / 80ms / 83ms |
| 읽은 키 표 인덱스 | 3,739 / 3,739 | 373 / 3,739 |
| `IOReportCopyChannelsInGroup` x3 | 137~169ms (순차) | 62ms (동시), 이후 캐시 |
| 탐색된 `Tg*` 센서 | 64 (84에서 절삭) | 84 |
| **보고 GPU 온도** | **53.73 / 53.56 / 53.38 C** | **53.63 / 53.45 / 53.34 C** |

GPU 온도 열이 `Tg*` 상한에 대한 수용 기준입니다. 실행 중 머신이 식고 있었기 때문에 세 판독값이 양쪽 모두 단조 감소하며, 각 단계의 전후 차이(0.10 / 0.11 / 0.04 C)가 연속 단계 사이의 드리프트보다 작으므로 값을 움직인 것은 상한 변경이 아닙니다.

**이슈의 9~11초 기준선은 이 하드웨어에서 재현되지 않았습니다.** 여기서 측정한 `IOReportCopyChannelsInGroup`은 호출당 약 45밀리초이고 이슈가 보고한 약 2.5초가 아니므로, 같은 세 호출이 7.5초가 아니라 137밀리초입니다. 이슈가 지목한 구성 요소들은 실재하며 이 수치들이 움직이는 대상이 정확히 그것들이지만, 이 머신의 절대 출발점은 9~11초가 아니라 1.4초였습니다. 원 보고 환경에서 확인할 가치가 있습니다.

## 5. 테스트

| 테스트 | 고정하는 것 |
|--------|-------------|
| `dropping_one_client_leaves_another_working` | 클라이언트 둘이 살아 있을 때의 회귀. 두 번째 클라이언트를 첫 번째가 드롭될 때까지 일부러 건드리지 않습니다. 리더가 이미 매니저를 캐시한 클라이언트는 우연히 계속 동작했기 때문에, 먼저 예열하면 버그를 가립니다 |
| `a_client_built_after_the_last_drop_still_works` | 같은 수명을 반대편에서 확인 |
| `discovery_stops_before_the_end_of_the_key_table` | 스캔한 키 수가 표 크기보다 작음 |
| `the_span_search_finds_what_the_full_scan_finds` | 빠른 경로와 전수 폴백이 실하드웨어에서 동일한 키 반환 |
| `channel_enumeration_happens_once_per_process` | `merged_channels()` 두 번 호출 간 포인터 동일성. 타이밍 단언이 아니라 직접 증거 |
| `each_subscription_copies_the_cached_channels`, `two_subscriptions_can_coexist` | 캐시가 구독에 그대로 넘겨지지 않음 |
| `name_prefilter_accepts_everything_the_classifier_can`, `every_candidate_name_sorts_inside_the_scanned_span` | 빠른 경로가 기대는 불변식 두 가지 |

하드웨어 의존 테스트는 SMC나 IOReport에 닿을 수 없는 환경(Intel Mac, VM, 샌드박스 러너)에서 깔끔하게 skip합니다.
